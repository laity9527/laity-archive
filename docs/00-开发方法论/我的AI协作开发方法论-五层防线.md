# 我的 AI 协作开发方法论：五层防线

作者：张磊
创建日期：2026-10-30
状态：定稿 v1.0（推导过程见 docs/01-研发日志/2026-10-30-方法论推导思考.md）

---

## 这套方法论解决什么问题

我用 Qoder 这类编程助手推进 Laity 项目时，反复遇到三类翻车：

1. 助手擅自换掉我定好的技术栈，或者顺手引入新依赖；
2. 一句"帮我做个 XX"，它替我做了二十个我没同意的隐含决策，埋到几千行代码之后才暴露；
3. 它报告"已完成、测试通过"，实际一跑就崩——它给自己打了满分。

我把这三个问题的根因归结为：**上下文缺失、目标模糊、验收主观**。后来在做软著留痕时又意识到第四个问题：**做完了，但拿不出证据证明是我主导创作的**。

对应这四个根因，我给自己定了五层防线。以后任何需求，都按这五层走，不跳步。

```
第 1 层：事实基座    —— 消灭"它不知道"
第 2 层：规格锁定    —— 消灭"目标模糊"
第 3 层：阶段闭环    —— 消灭"一口气生成然后崩盘"
第 4 层：验收门禁    —— 消灭"自我感觉良好"
第 5 层：过程存证    —— 消灭"做完了但证明不了"
```

核心心态：把编程助手当成一个执行力很强、但每次开工都失忆的初级工程师来管理。我不指望它自觉，我靠制度让它没法跑偏。

---

## 第 1 层：事实基座

助手每次会话都是失忆的。我不给它事实，它就拿训练数据里的"通用最佳实践"来填空，这正是技术栈被擅改的根源。所以项目根目录必须维护一份 AGENTS.md，助手会自动加载，内容只写事实与禁令，不写愿望。

我的 AGENTS.md 模板（按项目实际情况填空）：

```markdown
# 项目事实（必读，违反即返工）

## 技术栈锁定（不可替换，不建议升级）
- <前端框架及版本、UI 方案、状态管理>
- <后端框架及版本、ORM、数据库>
- 包管理：<pnpm/npm，禁止其他>

## 环境实况（方案必须适配，不许假设理想环境）
- 本地环境现状：<有/无 Node、Docker、数据库>
- 降级工作流：<无环境时：助手输出完整文件 → 我手动入库 → 有环境后回头验证>

## 目录与命名约定
- <分层结构、DTO/VO 规则、页面与组件存放位置>

## 视觉铁律（精确值，违反即返工）
- 色彩：背景 #FBFBF9 / 主字 #131313 / 辅助 #5C5C5C / 细线 #E7E7E2
- 形态：border-radius: 0；box-shadow: none；无渐变
- 字体：UI 用 Inter / 正文 Noto Serif SC 18px 1.85 / 时间与标签 JetBrains Mono
- 图标：禁用图标库，只允许字符 ↗ ← ● ○

## 合规与安全红线
- 依赖许可：MIT/Apache/BSD 可用；GPL/AGPL 一律禁止，引入前必查
- 前台数据访问只能走封装函数（如 getSafeLogs，内部强制 isPublished: true）
- Markdown 渲染必过 rehype-sanitize
- 上传图片禁止落服务器本地，走 OSS 外链
- 版本事实以 node_modules 内实际文档为准，禁止凭记忆使用旧 API

## 红线（任何阶段都不得触碰）
- 不得修改 build 配置、CI 配置、lockfile
- 不得顺手重构任务范围外的代码
- 不得新增依赖；确需新增，停下列出理由等我批准
- 数据库变更只出 SQL 迁移文件，不得直接执行

## 验证命令（验收唯一依据）
- <lint 命令 / 测试命令 / 构建命令 / 启动方式>
```

两条经验：

- **禁令比鼓励有效十倍。**"禁止引入新依赖"可被机械检查，"尽量用现有技术"只会被自由发挥。
- **视觉必须量化到能被 grep 检查。**助手对"简洁大气"有一万种理解，对 border-radius: 0 只有一种。不写精确值，产出一股模板味。

## 第 2 层：规格锁定

需求 → 规格 → 方案，三步各设一道确认门禁，助手在每个门禁必须停下等我，不许滑过去。

### 步骤 2.1：需求澄清（我发给助手的指令）

```
我要做的需求是：<一句话描述>。

你现在不许设计方案、不许写代码。只做两件事：
1. 用不超过 10 条要点复述你理解的核心约束（业务目标、用户角色、
   技术边界、明确的非目标）。
2. 列出最多 3 个会直接影响架构选型的阻塞性问题，按重要性排序。
   能从项目代码或 AGENTS.md 中找到答案的问题不许问我，自己先查。

我确认后你才能进入下一步。
```

### 步骤 2.2：规格文档

```
基于已确认的需求，产出 SPEC.md，包含且仅包含：
1. 功能清单：每条格式为「作为<角色>，我能<动作>，以便<价值>」，
   标注 P0（首个闭环必须）/ P1（后续阶段）/ P2（不做，写明理由）。
2. 数据模型：实体、字段、类型、关系，直接给出建表草案。
3. 接口契约：每个 API 的 method/path/入参/出参/错误码，用表格。
4. 明确的非目标清单（这次坚决不做什么）。

禁止出现"待定""视情况而定"——写不出来的列入阻塞问题问我。
产出后停下等我确认，不许开始设计或编码。
```

### 步骤 2.3：架构方案

```
基于已确认的 SPEC.md 和 AGENTS.md，产出 DESIGN.md，必须包含：
1. 架构决策记录：每个关键决策写三行——
   [决策] 选了什么 / [理由] 为什么（对比至少一个被否掉的备选）/ [代价] 接受了什么缺点。
   凡是 SPEC 或 AGENTS.md 已锁定的事项，不许重新决策。
2. 分阶段路线图：拆成 3-6 个 Phase，规则见下。
3. 每个 Phase 的验收标准：必须是「可执行命令 + 预期输出」或
   「可观察的具体行为」，禁止使用"稳定""健壮""良好"这类形容词。
4. 风险清单：每个风险给出触发条件和降级方案。

Phase 拆分硬性规则：
- 每个 Phase 结束时系统必须可运行、可演示、可回滚（git 可 revert）。
- Phase 1 必须是贯穿前后端的最小闭环（哪怕只有一条数据的增查），
  不许 Phase 1 只搭架子、Phase 2 只写实体类。
- 每个 Phase 列出「允许触碰的文件清单」，清单外文件一律不改。
- 单个 Phase 预估改动不超过 15 个文件；超了就继续拆。

产出后停下等我确认。
```

为什么坚持"Phase 1 = 最小纵向闭环"：横切分层（先全部实体、再全部服务）会让错误在最晚的时刻才暴露；纵向闭环让技术栈问题、联调问题在第一个 Phase 就炸出来，此时返工成本最低。

## 第 3 层：阶段闭环

长会话中助手会逐渐遗忘早期约束。所以每个 Phase 开新会话、重新注入约束，绝不在一个长会话里连做六个 Phase。

### 我的 Phase 执行指令卡（每个 Phase 复制一次，填空即用）

```
执行 Phase <N>：<名称>。

【上下文】先读 AGENTS.md / SPEC.md / DESIGN.md 的 Phase <N> 部分，
一句话复述交付物 + 允许触碰的文件清单，错了我会纠正。

【范围】只做本 Phase；范围外问题记 ISSUES.md，不许改；
不新增依赖，确需则停下报批。

【任务】按【任务 1】【任务 2】逐项交付：
- 每个文件：完整路径 + 完整内容（不许片段）
- 每个 .ts/.tsx 文件顶部带文件头注释（文件/描述/作者/创建日期/修改记录）
- 依赖未就绪的部分用 Mock 数据先行，标注哪些是 Mock、后续哪个 Phase 替换

【验收】逐条对照本 Phase 验收标准，粘贴实际执行的命令与真实输出；
没执行的标"未验证"。当前环境跑不了的，给出替代验证方式。

【留痕】交付末尾附一段 100 字以内的研发日志素材：
本 Phase 做了什么决策、遇到什么坑、如何解决的。我存入 docs/01-研发日志。

【停点】规格歧义 / 需改配置或依赖 / 验收达不成 → 立即停下问我。
停下来问是正确行为，不是失败；禁止用编造填补不确定性。
```

### 配套过程纪律

| 纪律 | 具体操作 | 防的是什么 |
|---|---|---|
| 一 Phase 一提交 | 验收通过立即 git commit，消息含 Phase 编号 | 回滚粒度；下一阶段改崩能一键退回 |
| 复述先行 | 每个 Phase 开头让助手复述范围，错了当场纠正 | 上下文稀释导致的范围漂移 |
| 问题外置 | 范围外发现只记 ISSUES.md 不动手 | "顺手重构"引入的隐性回归 |
| 拒绝合并 Phase | 助手说"下个 Phase 很简单我顺便做了"→ 拒绝 | 验收边界模糊，出错无法归因 |

## 第 4 层：验收门禁

助手报告的"已完成、测试通过"一律当作假设而非结论。验收标准在设计阶段就写成可机械执行的形式，且由我或独立审查会话执行，不让实现者自己给自己打分。

### 验收标准写法对照（我审 DESIGN.md 时的标尺）

| 不可验收（打回） | 可验收（通过） |
|---|---|
| 登录功能完善 | POST /api/login 传错误密码返回 401 + 错误码 AUTH_001；连续错 5 次锁定 15 分钟 |
| 性能良好 | 列表接口在 1 万条种子数据下 P95 < 300ms（附压测命令） |
| 代码质量高 | 测试全绿；lint 零 error；git diff --stat 不含允许清单外的文件 |
| 页面美观 | 1280px 和 375px 宽度下无横向滚动条，表单可完整提交 |

### 独立验收指令（开新会话）

```
你是独立审查者，不参与实现。审查 Phase <N> 的交付：
1. 运行 git diff <上个Phase的commit>..HEAD --stat，
   对照 DESIGN.md 中该 Phase 的文件清单，列出越界文件。
2. 逐条执行验收标准中的命令，粘贴真实输出，判定 PASS/FAIL。
3. 检查红线：有没有新增依赖、改配置、动 lockfile、范围外重构。
4. 视觉铁律核查：grep 交付文件中的 rounded-/shadow-/渐变类名与
   图标库 import，出现即 FAIL；抽查色值是否为规定精确值。
5. 留痕核查：新文件是否都有文件头注释；是否有本 Phase 的研发日志素材；
   本 Phase 是否形成独立 commit。
6. 输出结论：PASS / FAIL（附具体证据）。
   禁止因为"整体看起来不错"而放行 FAIL 项。
```

为什么开新会话审：同一会话里助手有维护自己先前输出的倾向，新会话没有历史包袱，审得更狠。

## 第 5 层：过程存证

这一层是为软著确权和日后维权加的，核心认知：**开发过程本身就是一台自动生产软著材料的机器**，过程留痕和代码正确性同等重要。

### 仓库证据结构

```
laity-archive/
├── docs/
│   ├── 00-开发方法论/       # 本文档所在：我的工作法与决策记录
│   ├── 01-研发日志/         # 每天记录：指令原文、思考、踩坑
│   ├── 02-测试记录/         # 功能自测表
│   ├── 03-功能截图/         # 真实运行截图（带地址栏）
│   └── 04-软著材料/         # 源代码文档、说明书
├── prisma/                  # 数据库模型
├── src/                     # 源码
└── docker-compose.yml
```

### 文件头注释铁律

每个手写或要求助手修改的 .ts/.tsx 文件，顶部必须有：

```tsx
/**
 * 文件：[文件名]
 * 描述：[组件或函数的具体作用]
 * 作者：张磊
 * 创建日期：2026-xx-xx
 * 修改记录：
 * - 2026-xx-xx: 创建并实现基础排版
 */
```

### 日常存证纪律

| 时点 | 动作 | 存到哪 |
|---|---|---|
| 每个 Phase 开始 | 把发出的指令原文存档 | docs/01-研发日志/日期.md |
| Phase 中踩坑 | 记「现象 → 根因 → 修复」，修错了的过程也记 | 同上 |
| Phase 验收通过 | 带地址栏的运行截图 + 自测表 | docs/03、docs/02 |
| 提交 | 用自己的一句话写 commit message，删掉工具自动生成的英文描述 | git 历史 |
| 内容发布 | SHA-256 内容哈希 + 服务器时间入库 | 数据库 contentHash 字段 |

两点心得：

- **修错的过程比修对的结果更有证据价值。**它证明是我在主导判断和取舍，这正是"独立创作"的核心。
- **提交记录要去工具味。**全中文、有个人真实感受的一两句话，比机器自动生成的英文翻译有力得多。

## 全流程串联

```
新需求
 ├─ 门禁1：助手复述约束 + ≤3 个阻塞问题 → 我确认
 ├─ 门禁2：SPEC.md（功能/数据/接口/非目标）→ 我确认
 ├─ 门禁3：DESIGN.md（决策理由 + Phase 路线图 + 可证伪验收标准）→ 我确认
 │
 ├─ Phase N（新会话 + 执行指令卡）
 │    ├─ 复述范围 → 交付代码 + 自测报告 + 研发日志素材
 │    ├─ 独立验收会话：命令核验 + 越界检查 + 视觉/留痕核查 → PASS
 │    └─ git commit（自己的话）+ 截图/日志归档
 └─ 全部完成 → 对照 SPEC 的 P0 清单端到端走查 → docs/04 整理成品材料
```

所有门禁——前三道确认（需求、规格、方案）加上每个 Phase 的验收——共同点只有一个：助手必须在门禁处停下等我。这是整套方法里最容易被破坏、也最需要我坚持的一点。

---

## 三个最容易翻车的细节（给自己提个醒）

1. **验收标准前置比验收动作严格更重要。**在设计阶段就逼助手写出可执行标准，会反过来约束它的实现——写不出验收标准的功能，往往就是它自己也没想清楚的功能，此时该拆需求而不是硬写。
2. **文件清单是比自然语言更硬的范围锁。**"只做登录模块"会被解释出花样；"只允许改这 8 个文件"可以用 git diff --stat 机械核查。
3. **给助手一个合法的"停下来"出口。**指令里明确"遇到不确定停下问我是正确行为"，否则它倾向于用编造来填满不确定性。"不编造业务逻辑"要写进每张指令卡，而不是只写在第一次对话里。
