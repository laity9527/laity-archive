# 个人信息与凭据泄露应急预案

作者：张磊
日期：2026-11-03
适用：Laity 项目档案库（laity.cn）在生产环境发生或疑似发生数据/凭据泄露时的处置
说明：这份预案是"照着敲"的清单，每一步都带判据；没有判据的步骤不算完成。
配套：日常门禁与部署见 `上线与回滚手册.md`，对外承诺见 `/privacy` 页。

---

## 一、先认清本站到底有什么可泄露

这决定了预案的严重程度，也决定了不要写做不到的承诺。

| 数据 | 在哪里 | 泄露后果 |
|---|---|---|
| 日志与项目文字内容 | 自有服务器 PostgreSQL | 作者本人的公开复盘外泄，无第三方个人信息 |
| 正文插图 | 阿里云 OSS（`logs/` 前缀，公共读） | 直链本身即可访问，泄露不额外扩大；但**对象名含时间戳与随机串**，不可枚举 |
| 管理员会话 | 访问者浏览器（签名 JWT） | 拿到 `NEXTAUTH_SECRET` 才能伪造会话，因此它是本站最高价值目标 |
| GitHub OAuth 凭据、数据库口令、OSS 子账号密钥 | 只在服务器 `.env.production` 与本地 `.env` | 口令/密钥泄露 → 按第三节处置 |
| 访问日志（IP、时间、UA、返回码） | nginx | 属常规运维日志，不含行为画像，不做分析 |

**本站不收集**：邮箱、手机号、密码、身份证、地址簿、位置、设备标识。没有用户注册，也没有第三方投稿。
所以"个人信息泄露"在本站的实际含义是：**管理员身份可被伪造，或作者自己的内容/凭据外泄**。

---

## 二、发现与判定（第一步永远是止血，不是查因）

1. **可疑迹象**：`/api/health` 异常或 503 频发、后台出现非本人操作的发布/下架/删除、OSS 出现来源不明的对象、
   nginx 日志里对 `/admin` 与 `/api/auth` 的大量非本人访问、GitHub 上该 OAuth App 出现异常授权记录。
2. **确认是否真被入侵**（只读取证，先别重启容器，重启会丢掉现场）：

   ```
   docker compose -f docker-compose.prod.yml ps                    # 有无异常容器/反复重启
   docker compose -f docker-compose.prod.yml logs --since 24h app  # 动作异常与堆栈
   sudo last -a | head -20                                         # 服务器登录来源
   sudo journalctl -u ssh --since "14 days ago" | grep -iE "accepted|failed" | tail -30
   sudo cat /root/.ssh/authorized_keys                             # 有无陌生公钥
   ```

   判据：能指出"哪个时间点、哪个入口、动了什么"。指不出来就按"疑似"继续，不要宣布无影响。
3. **数据库侧核对**：`publishedAt`/`updatedAt` 与内容摘要是否被改动——详情页的 SHA-256 就是为这一刻准备的：
   按 D5 口径（标题 + BEFORE + AFTER，UTF-8）独立重算，与库中 `contentHash` 比对。
   对不上说明正文在发布后被改过（正常编辑会退回草稿并保留旧摘要，见 D9）。

## 三、止血与凭据轮换（顺序不可颠倒）

1. **先断外网入口**：`docker compose -f docker-compose.prod.yml stop web`（只停 nginx，应用与库现场保留）。
   判据：`curl -I https://laity.cn` 不再返回 200。
2. **轮换被波及的凭据**（全部只能本人在控制台/服务器操作，AI 不代做、也不该看到值）：
   - `NEXTAUTH_SECRET` → 重新生成 ≥32 位随机串；**这一步会让所有已登录会话立即失效**，是真正的止血手段。
   - 数据库口令、OSS 子账号 AK、GitHub OAuth Client Secret → 按 `上线与回滚手册.md` 第七节 A/B 的顺序换。
   - 换完必须 `up -d --force-recreate app`：compose 只在创建容器时注入环境变量。
3. **清 GitHub 侧授权**：OAuth App 的授权列表里撤销不认识的设备/token。
4. 判据：新密钥能登录、能上传；旧 AK 在 RAM 控制台显示已禁用/已删除。

## 四、影响评估与通知（不承诺具体小时数）

- 本站是单人站，没有"受影响的用户"需要通知——**这一条要如实，不照抄平台型预案里的 72 小时通知义务**。
- 涉及以下情形时，按现行法规评估后**立即**（不晚于确认当日）报告属地主管部门，并视情况公告：
  1. 确认有第三方个人信息被处理或外泄（本站正常情形下不存在）；
  2. 服务器被植入、留存了陌生账户/公钥/定时任务（属入侵，按第五节走）；
  3. 发布内容被篡改且已对外可见一段时间（涉及作者本人署名的作品，需公告说明哪些时间段的内容不可信）。
- 记录一份《事件时间线》放进 `docs/01-研发日志/`：发现时间、判定依据、止血动作与时间点、轮换状态（**只记状态，不记任何密钥值**）、结论与后续改进项。

## 五、判定为入侵时不要试图"清理干净"

发现陌生公钥、陌生账户、异常定时任务或被篡改的系统文件时，改口令已经没有意义：

1. 立刻对数据库做逻辑备份并**离线**保存到服务器之外（备份文件本身按可疑样本处理，别在干净机器上执行）；
2. 保留日志与现场取证材料；
3. **重装系统后再上线**，不在被入侵的主机上原地清理；
4. 重装后所有凭据一律视为已泄露，全部轮换，再按 `上线与回滚手册.md` 第二节部署。

## 六、演练与保鲜

- 每半年走一次桌面推演：只做第二节的只读取证 + 第三节的 1、2 步（在预发或本地容器上做，不碰生产库）。
- 本预案引用的每一条命令与判据，都要能在当前编排文件里对上号；对不上就是预案过期，改文档而不是改口径。
