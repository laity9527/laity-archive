## 一、问题不是「标签太少」，是「标签不是分类」

- 56 个标签对应 13 条日志，平均每条 4–5 个标签，但 55 个只出现一次；
- 混进了 CSS 词元（`@container`、`flex gap`）、框架术语（`TurboPack`、`no-store`）与一次性事件（`first-entry`）；
- 结果：大厅筛选栏铺成三行、详情页「同标签相关」取不到 3 条、首页无法给出主题入口。

**结论：不删标签，先加一层“主题”**。主题是 8 个固定分类，标签仍是具体关键词；一个标签归属一个主题，一条日志可以由多个标签落到多个主题。

## 三、落地方式（不改数据模型）

1. **代码常量**：新增 `src/lib/topics.ts`，导出 `TOPICS` 与 `topicOfTag(tag)`；纯函数，可单测。
2. **派生而非存储**：日志的 `tags` 字段不动；列表页与首页按 `tags → topic` 现算，不新增数据库列、不跑迁移。
3. **写入时收口**：`normalizeTag` 已有去空白；追加三条——去掉开头的 `@`、单条日志最多 5 个标签、忽略大小写去重。**只对新写入生效**，不回改历史。
4. **界面**：大厅左栏先列 8 个主题（点击等价于按该主题下的标签集合做 OR），再给「全部 56 个标签」折叠区；首页只展示主题。
5. **验收**：56 个标签全部能映射到主题（脚本断言）；未映射数为 0；同标签相关日志的回退链在有主题后仍保留。

## 四、测试条目「测试AI帮我写」的处理建议

实读该条内容：BEFORE/AFTER 是多租户与 GitHub 认领的通用规划文本，经验总结就是「测试AI帮我写」，不是一次真实复盘。三种处置：

| 方案 | 动作 | 代价 | 建议 |
|---|---|---|---|
| A | 后台「下架」 | 从前台消失，保留摘要与发布时间，可恢复 | **推荐**：保留证据链，不丢历史 |
| B | 改标题 + 重写正文 | 需要补一次真实联调记录 | 若想保留“AI 写路径”的痕迹，选这个 |
| C | 彻底删除 | 正文与摘要一起消失，需回填 slug | 不建议：没必要销毁一次真实操作记录 |

无论选哪个，都建议在发布前检查里加一条提示：标题命中「测试 / test / demo」时要求二次确认。

**执行结果（2026-11-13）**：按方案 A 下架。首页已发布数 13 → 12，详情页返回 404；`contentHash` 与 `publishedAt` 均保留，可随时重新发布。
