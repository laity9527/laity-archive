# 上线与回滚手册

作者：张磊
日期：2026-11-03
适用：Laity 项目档案库在自有服务器上的首次上线（Phase 6b）与之后的每一次发版
说明：这份手册是"照着敲就行"的清单，每一步都带判据——没有判据的步骤不算完成。

---

## 一、上线前必须完成（缺一不可）

| # | 事项 | 判据 |
|---|---|---|
| 1 | 域名解析指向服务器公网 IP | `dig +short <域名>` 或 `nslookup` 返回该 IP |
| 2 | ICP 备案号取得并填入服务器 `.env.production` 的 `SITE_ICP` | 打开首页页脚能看到备案号，且链接指向 beian.miit.gov.cn |
| 3 | TLS 证书放到 `deploy/certs/laity.crt` 与 `laity.key` | 文件名与 `deploy/nginx.conf` 里两行 `ssl_certificate*` 完全一致 |
| 4 | 安全组只放行 22/80/443 | 云控制台截图或 `DescribeAcl` 结果 |
| 5 | SSH 关掉 root 口令登录与密码登录（步骤见第七节 B） | `sshd -T \| grep -E "permitrootlogin\|passwordauthentication"` 输出 `prohibit-password` 与 `no`；**做这步之前必须先用普通用户 + 密钥成功登录过一次** |
| 6 | 生产数据库口令非 root、长度 ≥12、与用户名不同 | 由编排里的 preflight 容器硬卡，不合格整个 `up` 直接失败 |
| 7 | 生产后台口令填入服务器 `.env.production` 的 `ADMIN_PASSWORD`（≥12 位，不与本地开发复用） | 浏览器在 `/login` 输这把口令能进 `/admin`；口令错时回到 `/login?error=CredentialsSignin`。2026-11-04 起不再需要生产 GitHub OAuth App（D20） |
| 8 | OSS 子账号密钥为**新轮换的那把**（步骤见第七节 A） | RAM 控制台里旧 AK 已禁用/删除；新 AK 上传成功且直链可匿名打开 |
| 9 | 本机四道门禁全绿 | `npm run lint`、`npx tsc --noEmit`、`npm run build` 退出码均为 0；`npm test` 全绿。推送后由 `.github/workflows/ci.yml` 自动跑同一套（含软著材料两步自检），CI 不过不发版 |
| 10 | 服务器能取到三个基础镜像 | `docker pull node:24-slim`、`postgres:16`、`nginx:1.27-alpine` 均成功，或本地已有同名镜像（`docker images` 可见）。本机 2026-11-04 复跑时 docker.io 直连不通，全靠事先经加速器拉取再 `docker tag` 成官方名（I019）——**这一步没确认就上去，`build` 与 `up` 会直接卡在拉取** |

## 二、部署步骤（服务器上，仓库根目录）

```
cp .env.production.example .env.production   # 填真实值，该文件不入库
docker compose --env-file .env.production -f docker-compose.prod.yml build app
docker compose --env-file .env.production -f docker-compose.prod.yml build migrate
docker compose --env-file .env.production -f docker-compose.prod.yml run --rm migrate
docker compose --env-file .env.production -f docker-compose.prod.yml up -d
```

**为什么 `build` 要分两条、且 migrate 必须点名（I026 结案说明）**：`migrate` 服务带着 `profiles: ["tools"]`，
不带服务名的 `docker compose build` 会**整个跳过它**——这正是历史上"连跑两次镜像 ID 不变"的来源：
compose 把迁移镜像构建到项目默认名 `laity-archive-migrate:latest`，而核对命令看的是 `:prod` 标签，
量的根本是 compose 不碰的那个标签。现已在编排里给 `migrate` 钉死 `image: laity-archive-migrate:prod`，
点名构建即可刷新该标签。每次发版仍建议核对一次：

```
docker images -q laity-archive-migrate:prod      # 构建前后比对，应变化
docker run --rm --entrypoint /bin/sh laity-archive-migrate:prod -c 'command -v openssl'
```

（在 Windows 的 Git Bash 里跑第二条要加 `MSYS_NO_PATHCONV=1` 前缀，否则 `/bin/sh` 会被改写成宿主路径；
服务器上不需要。）

**数据播种（I025 结案说明）**：生产库**不跑 seed**。migrator 镜像里没有 `src/` 目录，
而 `prisma/seed.ts` 按哈希单源要求 import 了 `../src/lib/content-hash.ts`，
在镜像里执行必然 `ERR_MODULE_NOT_FOUND`。这是有意的分层——测试种子属于本地开发（`npx prisma migrate dev` 会自动带上），
生产数据由后台录入。迁移本身不受影响：同一镜像在全新 postgres:16 上 `npx prisma migrate deploy`
输出 `All migrations have been successfully applied`（2026-11-04 容器实测）。

## 三、上线后核验

| # | 检查 | 期望 |
|---|---|---|
| 1 | `curl -i https://<域名>/api/health` | `200` 且 `{"status":"ok","db":true}`；头里有 `cache-control: no-store` |
| 2 | `curl -i https://<域名>/logs` | `200`，页脚有备案号与隐私入口 |
| 3 | `curl -s https://<域名>/robots.txt` | 三条 `Disallow`（/admin、/login、/api）+ `Sitemap` 行 |
| 4 | `curl -s https://<域名>/sitemap.xml` | 含 `/privacy` 与全部已发布日志；不含草稿与 `/admin` |
| 5 | 存证复核 | 任取一条日志，按 D5 口径（标题\nBEFORE\nAFTER，UTF-8）独立重算 SHA-256，与详情页印章逐字符一致 |
| 6 | 草稿隔离 | 后台新建一条不发布 → 首页/大厅/项目页/站点地图都搜不到，直接访问返回 404 |
| 7 | 下架 | 后台点「下架」→ 前台立即 404，站点地图下次请求后不再出现；历史摘要与时间仍在库中 |
| 8 | 上传 | >1MB 且 <5MB 的 png 能成功；改名伪装成 .png 的非图片返回 IMG_001；服务器本地无新文件 |
| 9 | `docker compose ps` | app/db/web 均 `healthy`/`Up`。这里的 `app healthy` 已经等于"应用真连得上库"（探针解析 `/api/health` 的 `db` 字段），不再是"进程活着"的弱信号 |

## 四、回滚

1. 只回滚应用：`git checkout <上一个可用提交> && docker compose --env-file .env.production -f docker-compose.prod.yml build app && docker compose --env-file .env.production -f docker-compose.prod.yml up -d app`；
2. 数据库不动——迁移只增不改破坏性字段（Prisma 迁移均为向前追加），因此回滚代码不需要回滚库；
3. 若问题出在编排或 nginx：`docker compose ... restart web`，配置改动用 `nginx -t` 先校验再 reload；
4. 每个 Phase 一个独立提交是既定纪律，回滚目标永远是"上一个 Phase 的提交"，不做跨阶段连环回退。

## 五、备份与恢复

```
# 备份（建议 cron 每日一次，产物传到服务器之外）
docker compose -f docker-compose.prod.yml exec db pg_dump -U laity_app -d laity -Fc > backup/laity-$(date +%F).dump

# 恢复
docker compose -f docker-compose.prod.yml exec -T db pg_restore -U laity_app -d laity --clean --if-exists < backup/laity-<日期>.dump
```

图片对象在 OSS 侧，靠存储桶版本控制或跨区复制保护，不随数据库备份走。

## 六、常见故障定位

| 现象 | 先查 |
|---|---|
| 后台点了没反应、服务端无异常 | 是否动作被同源校验拒了：`deploy/nginx.conf` 已补 `X-Forwarded-Host`（I033），线上未复验 |
| 预演或清理时把开发容器一起删了 | compose 的项目名默认取**所在目录名**，生产与开发编排同目录即同项目，`-f docker-compose.prod.yml down` 会连带清掉开发栈的容器。已在生产编排里钉 `name: laity-prod` 隔开；数据卷不在本次声明的卷列表里时不会被删，恢复只要 `docker compose up -d` 重挂原卷 |
| 输完口令回到 `/login?error=CredentialsSignin` | `ADMIN_PASSWORD` 与输入不一致；**未配置或为空时也是一律拒绝**（`src/lib/admin-password.ts` 空值不放行）。页面只说"口令不正确"、不区分原因，是故意的——不给猜口令的人反馈 |
| 登录成功却马上被弹回 `/login` | 会话 cookie 没被带上或验不过：`NEXTAUTH_URL` 不是 `https://` 正式域名（v4 只在 https 下发 `Secure` cookie，浏览器便不回传）、或换过 `NEXTAUTH_SECRET` 使旧 cookie 全部失效。原先"GitHub 授权页 404 是 `GITHUB_ID` 手抄失真"那一行随 D20 作废，本站已没有 OAuth 回调 |
| 本机 dev 里连错几次口令后，**输入正确口令也返回 401** | 应用层登录节流生效（同一来源 10 分钟内 5 次失败即拒绝，成功登录会清零）。计数在进程内，重启 dev 立刻清空；生产的第一道是 nginx 的 `limit_req`（见上一行），两者表现不同：代理超限回 429，应用超限回 401 且与"口令错"一模一样 |
| 后台连点几次登录就返回 429（页面显示"登录没有完成"或浏览器直接给 429 页） | 是 `deploy/nginx.conf` 的登录限速在生效：`location = /api/auth/callback/admin` 按来源 IP `rate=5r/m` + `burst=5 nodelay`。**这些请求根本不进应用**，所以应用日志里查不到对应条目、nginx 日志里是一串 429——这恰好也是"有人在猜口令"的信号。真人手滑等 12 秒即可恢复；要放宽只改 rate/burst，不要改成不限 |
| 本机 `npm run dev` 时 `/login` 反复整页重载 | 把 dev 的标准输出重定向到了**仓库内**的文件（如 `tmp/dev.log`）：Turbopack 监视整个项目目录，日志写入 → 触发重编译 → Fast Refresh 让浏览器重载 → 又写日志，形成回环。改写到目录外即断（实测循环由 ~7.5 次/秒降为 0）。`tmp/` 只是 gitignore 与 lint 排除，**不受监听**这条不成立 |
| 上传报"缺少环境变量 OSS_REGION" | `.env.production` 是否填了四项；改过要 `up -d --force-recreate app`（compose 只在创建容器时注入） |
| 上传成功但图片 404 | `OSS_REGION` 是否为 `oss-cn-beijing`（写成 `cn-beijing` 会拼出不存在的域名）；Bucket 是否公共读 |
| 迁移像跑了却没生效 | 回到第二节的 I026：镜像标签是否真被刷新 |
| `/api/health` 返回 503 | 数据库容器健康检查与 `DATABASE_URL`；此时页面会显示加载失败而不是伪装成 404，属诚实失败 |

## 七、凭据轮换与 SSH 加固（第一节第 5、8 项的展开）

这两件事都是外部系统动作，只能本人做；**顺序不能颠倒**，每步做完要看到判据再走下一步。

### A. 阿里云 AccessKey 轮换

爆炸半径先想清楚：这把密钥属于子账号，只有 `oss:PutObject` 且资源限定 `acs:oss:*:*:laity-archive/logs/*`——
泄露了别人既删不掉也列不了，但能往 `logs/` 前缀写脏对象并产生存储费。要换，不必慌。

| 步 | 动作 | 判据 |
|---|---|---|
| 1 | RAM 控制台看旧 AK 的"最后使用时间"（6b 未上线，应为从未使用） | 截图或记录 |
| 2 | **新建第二把，旧的先留着**（同一子账号，策略不动） | 两把 AK 并存 |
| 3 | 新 ID/Secret 只写进本地 `.env` 与服务器 `.env.production` | 不进对话、不进仓库、不贴工单 |
| 4 | 本地 `docker compose up -d` + `npm run dev`，登录后台点一次上传 | 成功且直链可匿名打开 |
| 5 | 旧 AK 先**禁用**而非删除，观察 1–2 天无报错再删 | 前台上传与历史直链均正常 |
| 6 | 控制台查"AccessKey 泄露 / 安全体检"有无平台侧告警 | 无告警；有则按平台处置流程走 |

第 4 步的两个分支：报 `AccessDenied` → 查子账号是否仍挂着那条 `PutObject` 策略；
上传成功但直链 404 → 查 `OSS_REGION` 是否为 `oss-cn-beijing`（写成 `cn-beijing` 会拼出不存在的域名）。
服务器上改过 `.env.production` 之后必须 `--force-recreate`——compose 只在**创建容器时**注入环境变量：

```
docker compose --env-file .env.production -f docker-compose.prod.yml up -d --force-recreate app
```

### B. 服务器：先保住登录，再关密码

⚠️ 顺序错了会把自己锁在门外。核心保险是**改配置时留着一个已登录的老会话别关**，新终端验证通过才继续。

1. 本机生成一把**新名字**的密钥（别复用可能进过对话的那把）：`ssh-keygen -t ed25519 -f ~/.ssh/laity_vps -C "laity-vps-2026"`
2. 用现有口令登进去，建非 root 管理用户并装公钥：`sudo adduser ops && sudo usermod -aG sudo ops`（CentOS/Alma 系用 `wheel`），
   再写 `/home/ops/.ssh/authorized_keys`，权限 `700` 目录 / `600` 文件 / 属主 `ops:ops`
3. **验证闸门一**：另开终端 `ssh -i ~/.ssh/laity_vps ops@<IP>` 能进，进去 `sudo -v` 通过。**不通过不要往下走**
4. Ubuntu/Debian 用 drop-in 比改主文件稳：`/etc/ssh/sshd_config.d/60-hardening.conf` 写
   `PermitRootLogin prohibit-password`、`PasswordAuthentication no`、`KbdInteractiveAuthentication no`、`AllowUsers ops`。
   sshd 是**第一次出现即生效**：主配置顶部的 `Include` 会让 drop-in 盖住后面同名项，`AllowUsers` 只能有一处有效
5. 先校验再重载，不要直接 restart：`sudo sshd -t` 通过后 `sudo systemctl reload ssh`（RHEL/Alma 服务名是 `sshd`），
   再 `sudo sshd -T | grep -Ei "permitrootlogin|passwordauthentication|allowusers"` 看实际生效值
6. **验证闸门二**：全新终端 `ssh -i ... ops@IP` 必须成功、`ssh root@IP` 输密码必须被拒。
   任一不对，回到步骤 2 那个还活着的老会话删掉 `60-hardening.conf` 再 reload——这就是留老会话的全部意义
7. 最后才 `sudo passwd root`（纵深防御）。若走阿里云 ECS 控制台的"重置实例密码"，**该操作要求重启实例**，
   所以必须先做完 3–6 再重启，否则重启后又回到可爆破状态
8. 安全组只放 22/80/443；更稳的做法是把 22 的源地址限到自家出口 IP（22 对全网开放时爆破是常态，日志里看得到）
9. 比改口令更值得查的一件事——机器上有没有别人留的东西：

```
sudo cat /root/.ssh/authorized_keys                       # 有没有不认识的公钥
sudo last -a | head -20                                   # 历史登录来源
sudo journalctl -u ssh --since "14 days ago" | grep -iE "accepted|failed" | tail -30
```

发现陌生公钥或异常登录，改口令就没意义了——按入侵处置来（离线备份、重装、再上线）。

### C. 两件连带的

- **数据库口令一起换**：若 `.env.production` 的 `POSTGRES_PASSWORD` 曾与 root 口令同值或同构，一并换掉。
  编排里的 preflight 硬卡三条：非 `root`、口令 ≠ 用户名、长度 ≥12（见 `docker-compose.prod.yml`）。
- **留档口径**：做完只在 `docs/02-测试记录/Phase-6-环境准备自测表.md` 补一行状态，
  写"AK 已于 x 月 x 日轮换、旧密钥已删除""SSH 已关密码登录与 root 口令登录"这个级别，**不写任何 ID 或值**。
