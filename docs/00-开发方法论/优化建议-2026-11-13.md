## 二、逐项建议

### O1（P1）日志大厅：列表不取正文、加重上限

**现状（证据）**

- `src/lib/logs.ts:54` 的 `getSafeLogs` 用 `db.log.findMany({ where, orderBy, include })`，
  **既没有 `take`，也没有 `select`**——Prisma 默认返回全部标量列，包括两个长文本字段
  `beforeContent` / `afterContent`（种子数据里单篇正文可达数千字）。
- `src/app/logs/page.tsx:237` 的 `logs.map(...)` 一次性渲染全部结果，没有分页/截断。

**影响**：日志从 12 篇涨到 200 篇时，大厅首屏会拖回数百篇正文（数 MB 级），
序列化与 RSC 传输都按全量走；手机网络下首屏明显变慢，且与"大厅只列标题/日期/标签"的实际需求不符。

**建议改法（可执行）**

1. 在 `src/lib/logs.ts` 新增列表专用查询 `getLogList(params)`：
   - `select` 白名单：`title`、`slug`、`tags`、`beforeDate`、`afterDate`、`publishedAt`、
     `project: { select: { name, slug, kind, status } }`、`user: { select: { handle } }`；
   - `take: 50`（常量 `LOG_PAGE_SIZE`），游标用 `beforeDate + id` 或 `page` 参数；
   - 保留现有 `getSafeLogs` 给"需要正文"的调用方（搜索片段、导出以外的少数场景）。
2. `src/app/logs/page.tsx` 改调 `getLogList`，列表下方加"下一页/上一页"（沿用现有 `logsHref` 拼参数）。
3. 搜索路径单独处理：命中片段需要正文，建议"先按 `q` 取候选（仍限 50 条）再取正文"，
   或直接用 Prisma `contains`（`mode: "insensitive"`）把过滤下推到数据库，命中后再取片段。

**验收**：`/logs` 首屏响应中不出现 `afterContent`；`?page=2` 可取到第 51–100 条；
`npm test` 154/154；`npm run build` 0。

**成本/风险**：改 2 个文件、约 80–120 行；搜索语义要从"全量内存匹配"改成"限量大池匹配"，
需同步更新 `docs/02-测试记录` 的搜索验收口径。

### O2（P1）大厅筛选项：不要再全量查一遍

**现状（证据）**：`src/app/logs/page.tsx:66` 先 `const all = await getSafeLogs()`，
用它算 `projectOptions`（`all.map`）与 `tagOptions`（`all.flatMap`）；随后第 67–71 行
在筛选/搜索时**再查一次**。

**建议改法**：新增轻量 `getLogFacets()`——一次 `findMany` 只 `select { tags, project: { select: { slug, name } } }`
（仍限已发布），或 `groupBy` + `distinct`；页面改为"facets 一次 + 列表一次"，
筛选态总查询数从 2 次降到 2 次但**载荷从全文字段降为两列**，未筛选态从"1 次全量"降为"1 次轻量 + 1 次分页"。

**验收**：筛选态 SQL 日志中 `beforeContent` 不再出现；`/logs?tag=...` 与 `/logs?q=...` 结果与现状一致。

### O3（P1）导出失败：补一条不含数据的服务端日志

**现状（证据）**：`src/app/admin/export/route.ts:45` 是 `} catch {`，直接返回
`500 {"error":"EXPORT_001"}`，**没有任何 `console.error`**。线上出现导出失败时，
运维只能看到 500，无法区分"库连接失败 / 序列化失败 / 权限字段缺失"。

**建议改法**：`catch (error)` 后加一行 `console.error("[export] 导出失败", error instanceof Error ? error.message : error)`，
**只记消息、不记 payload、不记 token**；错误码与前端文案不变（EXPORT_001 的既定口径不动）。

**验收**：人为在本地让查询抛错（如临时改表名）→ 服务端出现一条 `[export]` 日志，响应仍是 500 + EXPORT_001。

### O4（P2）补两条数据库索引（需负责人执行迁移）

**现状（证据）**：`prisma/schema.prisma:110-113` 只有
`@@index([userId, isPublished, beforeDate])` 与 `@@index([projectId])`。
全局大厅查询是 `where: { isPublished: true } orderBy: { beforeDate: "desc" }`（无 `userId`），
**用不上以 `userId` 开头的复合索引**；`tags: { has }` 也没有 GIN 索引。

**建议改法**（一次迁移，两条索引）：

```prisma
@@index([isPublished, beforeDate])
@@index([tags], type: Gin)
```

**验收**：`EXPLAIN` 显示大厅查询走 `isPublished_beforeDate_idx`、标签判定走 GIN；
迁移由负责人本地执行 `npx prisma migrate dev --name add_hall_indexes` 并提交迁移文件。

**成本/风险**：数据量小，建索引瞬时；GIN 会让写入略慢（个人站可忽略）。
**不做也不会坏**，属"数据涨到几百篇后再看"的项。

---

### O5（P2）sitemap：一次批量查询替代逐用户 N+1

**现状（证据）**：`src/lib/sitemap-data.ts:54-72` 对每个用户串行调用
`getSafeLogs({ handle })` 与 `listPublicProjects(id)`，而前者会把**全文**查回来，
只为拿 `slug` 与 `updatedAt`。

**建议改法**：直接一条 `db.log.findMany({ where: { isPublished: true }, select: { slug, updatedAt, user: { select: { handle } } } })`
加一条 `db.project.findMany({ select: { slug, createdAt, user: { select: { handle } } } })`，
在内存按 handle 分组；不再复用前台的全文查询。

**验收**：`/sitemap.xml` 条目数与现状一致（含 `/u/<handle>/...`），响应时间与查询数下降。

### O6（P2）标签前置判定与 O4 配套

未落地前，标签数 < 100 时全表扫也可接受——**与 O4 同批做，不单独行动**。

### O7（P3）看板取数：数据涨了再聚合

`getArchiveBoard`（`src/lib/projects.ts:127-165`）把每个项目的全部已发布日志的 `beforeDate`
查回内存再取 `[0]` 与 `length`。个人站项目数十级、日志数百级时无感；
若日志破千，改为 `groupBy({ by: ["projectId"], _count, _max: { beforeDate } })` 一次聚合。
**当前不建议动**——避免为不存在的规模付复杂度。

### O8（P3）把"性能预算"写进事实基座

建议在 `AGENTS.md`「验证命令」节补三行可核对阈值（需点名授权后执行）：

- `/logs` 首屏查询数 ≤ 2、响应体不含 `afterContent`；
- 任一前台页面的 Prisma 查询数 ≤ 3（不含 Proxy 的前置判定）；
- sitemap 查询数 ≤ 3（与用户数无关）。

这三条能把 O1/O2/O5 的验收从"感觉快了"变成"可数的门禁"。

## 四、不建议做的事

- **不引入 Redis/进程内缓存**：本站是单实例个人站，缓存失效逻辑比收益贵；
  真要提速，先做 O1 的"少查字段"。
- **不引入全文检索扩展/依赖**（pg_trgm、Meilisearch 等）：在 O1 的分页上限下，
  `contains` 足够；等日志破千再评估。
- **不把 PPR 改成全动态**：现有 `Cache Components + connection()` 口径已稳定，
  为性能改渲染模式会牵动软著材料与整站缓存语义。
- **不为"代码更优雅"重写 `getSafeLogs` 的调用方**：本轮只做载荷与上限，不做分层重构。
