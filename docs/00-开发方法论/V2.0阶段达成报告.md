## 二、核心架构演进

### 2.1 数据层：从"一张表服务一个人"到租户复合键

- 新增 `User` 表；`Project` / `Log` 加 `userId`；`slug` 由全局唯一改为 `@@unique([userId, slug])`（租户内唯一，不同账号可以撞同名 slug）。
- 存量数据通过独立回填脚本挂到旧账号（zhanglei）名下，12 篇日志一条不丢；`userId` 先可空、Step 4 收 NOT NULL。
- 三个迁移按序入库：`init_v2_multi_tenant` → `add_github_id` → `step5_sync_foundation`。
- 踩过的坑：`add_github_id` 在 4-A 生成后一直处于未跟踪状态，4-B 提交前盘点工作区才拦下——迁移不入库，服务器 `migrate deploy` 会缺列，登录建号直接失败。

### 2.2 路由层：从 `/logs/[slug]` 到 `/u/[handle]/...`

- 前台全部迁到租户前缀：`/u/[handle]`、`/u/[handle]/logs/[slug]`、`/u/[handle]/projects/[slug]`。
- Proxy 的 matcher 与 404 文案按租户段解析；草稿隔离与真 404 仍在守卫层判定（Cache Components 下页面级 `notFound()` 只能 200 + 错误页）。
- 踩过的坑：4-B 编辑页"看前台"链接漏改旧路由，顺手修正；`refreshLogViews()` 仍在失效已退役的 `/logs` 路径上做 revalidate——静默无效，已挂 I079 不擅自改（租户页缓存语义未实测）。

### 2.3 鉴权层：两代人走过的弯路

演进链：**管理员口令（V1）→ 取消 GitHub 登录（D20 过渡态）→ GitHub OAuth 回归（4-A）**。

- 4-A：`GitHubProvider` + 首次登录认领/建号（githubId → handle → 新建），`ConsoleSession = Session & { userId }`，`isAdmin` 从会话与准入中退役（库字段保留不迁移）。
- 4-B：`requireAdminSession()` 改判 `userId` 存在性；Proxy 守卫同步改判 `token.userId`，与动作层同源；后台每页自查会话（Next 16 布局与页面并行渲染，布局 redirect 拦不住页面取数）。
- 踩过的坑（两处，都是"认领静默跳过"）：
  1. **v4 jwt 回调的 `user` 是归一化对象**（只有 id/name/email/image），GitHub 原始资料在独立的 `profile` 参数——读 `user.login` 恒 undefined，认领整段被 `if` 静默跳过，会话没有 userId，Proxy 弹回 /login。修复：改读 `profile`，并加 try/catch 落日志后原样上抛。
  2. **GitHub login ≠ 站内 handle**：登录名 laity9527、旧账号 handle 是 zhanglei，认领链第二环 miss 会新建空账号。经本人批准做一次性绑定 `githubId=111046902`；生产库部署时需跑同一条 UPDATE。
- `iss` 不是根因：4.24.15 的 GitHubProvider 默认已带 `issuer`，RFC 9207 校验本来就通过——显式钉住只是防未来漂移。

### 2.4 写路径隔离：0 行即不存在

- 六个写动作（saveProject / deleteProject / saveLog / publishLog / unpublishLog / deleteLog）全部从会话取 `userId`，写入一律用 `{ id, userId }` 复合条件；`updateMany / deleteMany` 命中 0 行按资源不存在返回（LOG_002 / PRJ_004）。
- 跨账号构造 id 与请求不存在的记录得到**同样结果**，不泄露存在性；删除仍保 P2003 → PRJ_001 的"项目下还有日志"判定。
- 读取侧：后台四个页面与全部 DAL 函数按 `userId` 过滤；公开查询走显式 `select` 白名单（D10 口径不变）。

### 2.5 存储隔离与同步引擎（Step 5）

- OSS 对象键由 `logs/<YYYY-MM>/...` 改为 `logs/<userId>/...`；RAM 策略资源 `logs/*` 仍覆盖，**云端无需改动**。恶意 userId（`../evil` 等）被逐段断言拒绝，已进回归测试。
- 同步引擎三件套：
  1. **token 底座**：OAuth 回调截获 `account.access_token` → AES-256-GCM 加密落库（`githubAccessToken`）；密钥 `ENCRYPTION_KEY`（64 位 hex）只进环境变量，preflight 硬卡形态；token 不进 JWT / session。
  2. **同步引擎**：`/user/repos`（公开、最近推送前 30）+ 逐仓库 commits（限并发 5、超时 10s）；四道过滤（去 merge、去 <10 字符与黑名单、按 sha 去重、同仓库同日合并）；草稿挂 `github-sync` 虚拟项目；`sourceCommitSha` + 租户内唯一索引做幂等锚点。
  3. **UI 与文档收口**：概览页 [ 从 GitHub 同步 ] 按钮 + `?synced/skipped` 横幅；隐私页与说明书按"加密落库、仅拉公开提交"改写；SPEC 新增 F20。
- 踩过的坑（Step 5 调试轮，全部实测定位）：
  1. **scope 不足**：默认 `read:user user:email`，commits 接口 404；补 `public_repo`（不引 `repo`），存量用户须重登一次。
  2. **`encodeURIComponent(repo)` 把斜杠编码成 `%2F`**，GitHub 不认 %2F 为路径分隔符 → 404。这是 `synced=0&skipped=0` 的真根因，去掉编码即通。
  3. **`sourceCommitSha ?? null` 会清锚点**：表单编辑一条已同步草稿时字段为 undefined，若照写 null 就去重失效。改成条件展开，只在显式提供时写入。
  4. author 过滤不可靠：GitHub commits 的 `author` 参数匹配 git author 信息而非 login，邮箱不一致全灭——最终去掉该参数，去重交给 `sourceCommitSha`。
  5. **软著窗口第十六次配平**：新文件把 ①+② 顶过 1500 行，auth/proxy 面临折走。经负责人两次裁定，github-sync-filter / github-sync / logs 三件让位进 ③，确保 content-hash / publish / projects / auth / proxy 整份可见。

### 2.6 生产编排随变更同步

- `docker-compose.prod.yml`：ADMIN_PASSWORD 退役、GITHUB_ID/SECRET 与 ENCRYPTION_KEY 透传（`${VAR:?}` 前置失败）；preflight 改为"GitHub 两键非空 + ENCRYPTION_KEY 64 位 hex"。
- nginx 限速端点随之改到 OAuth 回调 `/api/auth/callback/github`（原 admin 回调端点已死，限速会形同虚设）。
- 本地实测：齐备哑值 → compose config 退出 0；缺 ENCRYPTION_KEY → 退出 1 并指明缺项。

## 五、Step 6（AI 辅助生成）的现成接口

如果按当前架构接 AI，可直接复用的东西：

1. **输入已就位**：同步草稿的 `afterContent` 是当天 commit 首行清单，`title` 是首行；`sourceCommitSha` 保证幂等，重复生成不会重复建行。
2. **写入无需新通道**：生成结果走既有 `saveLog`（表单同一入口），只是把"（等待补充）"换成 AI 文本；草稿隔离、发布存证、敏感信息扫描全链路自动生效。
3. **需要先定的三件事**（建议立项前裁定）：
   - 触发点：同步完成后自动生成，还是编辑页手动点一次（后者可控、可算账）。
   - 模型与成本：调用外部 API 意味着新增出网依赖与按次计费，属"新增依赖/外部服务"红线，需要单独报批。
   - 失败降级：AI 不可用时草稿保持占位文本，不阻塞同步主流程（与现有 `failedRepos` 降级同一哲学）。
4. **一个提醒**：AI 生成的正文一旦发布就会进入 D5 摘要口径，发布即存证——生成内容是否要标注"AI 辅助"属于对外承诺问题，建议在 SPEC 层面先定。

## 六、结论

V2.0 把"单人档案库"变成了"多租户、可自助同步"的形态，四层隔离（数据 / 路由 / 鉴权 / 存储）全部落地并有测试与实测背书；七条 Step 5 提交在经历 4 轮真实缺陷修复后收口。当前不是"没有遗留"，而是遗留全部**有名有姓、有判据、有状态**——14 条 OPEN 里没有一条是"不知道该怎么验"。
