## 三、Step 6（AI 辅助生成）前置决策

现成可复用的接口已在《V2.0 阶段达成报告》第五节写明：草稿的 AFTER 是 commit 首行清单（原料）、写入走既有 `saveLog`、`sourceCommitSha` 保证幂等。以下是**需要负责人逐项裁定**的六件事：

### 决策 1：触发点
- **A（推荐）**：编辑页手动点「AI 生成」——单次可控、可算账、失败不影响同步主流程。
- B：同步完成后自动生成——省一步操作，但同步耗时不可控，且每次同步都会产生模型费用。

### 决策 2：模型接入方式（新增外部依赖，属红线，需报批）
| 选项 | 隐私/数据边界 | 成本 | 部署复杂度 | 风险 |
|---|---|---|---|---|
| A 商用托管 API（按量计费） | 正文与 commit message 会发给第三方；隐私页必须如实改写 | 按 token 计费，可设上限 | 低（一个 HTTP 客户端） | 数据出境与条款变更 |
| B 国内合规托管 API | 同 A，但备案与内容审核链路更顺 | 同上 | 低 | 条款与配额 |
| C 本地小模型（自托管） | 数据不出服务器，隐私最稳 | 无按次费用，需算力 | 高（镜像体积、内存、加载时长） | 1C1G 服务器跑不动 |
| D 暂缓 | — | — | — | Step 6 不启动 |

当前服务器最低配是 1 核 1G，选项 C 基本不可行；若选 A/B，需在 `docker-compose.prod.yml` 与 preflight 里加新键，并同步隐私页与说明书（"AI 辅助"属对外承诺，必须在页面上说清发送了什么）。

### 决策 3：生成范围
- **A（推荐）**：只生成 BEFORE 与 AFTER 两段正文（标题保留 commit 首行）。
- B：连 `lessonLearned` 一起生成——但"经验总结"是存证语义的一部分，AI 代笔会让"这是作者本人的判断"这句话失实。

### 决策 4：失败与降级
保持"（等待补充）"占位，同步主流程不因 AI 不可用而失败——与现有 `failedRepos` 降级同一哲学。生成结果仍走草稿，**不自动发布**。

### 决策 5：对外标注
若采用方案 A/B，建议在详情页印章区或正文末尾标注"本段由 AI 辅助生成、作者审校"。是否标注是产品/合规决策，需在 SPEC 里先落一条 F 编号。

### 决策 6：成本上限
建议硬性约束：单次同步生成的草稿数上限（当前同日合并后 12 条左右）、单条正文长度上限（沿用 `LIMITS`）、每月总调用次数告警线。这些数值需要负责人给定，否则第一版就会失控。

## 四、建议的 Step 6 最小闭环（供参考，不是计划）

若选"决策 1-A + 决策 2-A + 决策 3-A + 决策 4 降级 + 决策 5 标注"：新增一个 `src/lib/ai-rewrite.ts`（纯函数拼 prompt + 一个薄客户端）、编辑页一个按钮、一个 Server Action（会话校验 → 读草稿 → 调用 → 写回 BEFORE/AFTER 草稿字段，不发布）、隐私页与说明书同步、SPEC 新增 F 编号。预计三条 commit，与 Step 5 的切片节奏一致。
