## 一、功能一：搜索关键词高亮

### 1.1 现状实测

- 搜索链路：`src/app/logs/page.tsx` 的 `LogBoard`（Server Component，`Suspense` 内请求期取数，
  PPR 静态壳 + `cacheComponents`）→ `src/lib/logs.ts:searchLogs` → `src/lib/log-search.ts:matchLog`
  （纯函数，title/beforeContent/afterContent/tags 四字段大小写不敏感**子串**匹配，内存层完成）。
- 大厅列表行当前只显示：项目名、**title（h2 链接）**、tags。**beforeContent/afterContent 不在列表展示**。
- `getSafeLogs` 对 Log 本体无 `select` 白名单（只 `include` project/user.handle），正文字段已在手，
  片段切分不需要新增查询。
- Markdown 渲染唯一出口是 `src/lib/markdown.tsx`（react-markdown + rehype-sanitize），仅供详情页。

### 1.2 展示落点（对现有列表行的增量）

每条搜索结果行：

1. **title**：全量展示，命中词包 `<mark>`（title 本来就整条展示，无需片段）。
2. **beforeContent / afterContent**：**新增一行片段**——仅当该字段内存在命中时展示；
   取首个命中位置前后各 60 字符为窗口，越界侧补 `…` 前缀/后缀，窗口内命中词包 `<mark>`。
   片段是**纯文本**展示，不经过 Markdown 渲染器（避免 Markdown 语法被渲染成 HTML 的旁路）。
3. **tags**：不参与高亮（本轮只点名 title/before/after），维持原样。
4. 匹配只发生在 tags 字段时：不显示片段行（tags 原样可见，读者能看到为什么命中）。

### 1.3 服务端做还是客户端做：服务端

| 判据 | 事实 |
|---|---|
| 数据流 | 搜索本就在服务端请求期完成（`searchParams` Promise + Suspense），高亮是取数后的纯文本变换，天然在同一侧 |
| 客户端负担 | 分段结果是可序列化纯数据，RSC 直接渲染 `<mark>`，**零客户端 JS、零 island** |
| 可测性 | 纯函数进 `src/lib`，`node --test` 直跑（项目惯例：可测逻辑必须住 src/lib，I027/路径坑） |
| PPR 兼容 | 高亮在请求期片段内计算，静态壳不含搜索结果，无缓存语义变化 |

### 1.4 纯函数隔离方案（新增 `src/lib/highlight.ts`）

```ts
type Segment = { text: string; match: boolean };

// 把 text 按 query（大小写不敏感子串）切成交替段；保留原文大小写；空 query 返回单段 match:false
export function highlightSegments(text: string, query: string): Segment[];

// 取首个命中处前后 radius（默认 60）字符的窗口；无命中返回 null。
// 返回 { segments, leadingEllipsis, trailingEllipsis }，segments 已按 highlightSegments 切好
export function extractSnippet(
  text: string, query: string, radius = 60,
): { segments: Segment[]; leadingEllipsis: boolean; trailingEllipsis: boolean } | null;
```

实现口径（三条硬约束）：

1. **用 `indexOf` 循环，不构造正则**——查询词是用户输入，拼进 RegExp 会引入正则注入与
   ReDoS 两个面；`indexOf` 对 `a.b(*` 这类输入天然按字面处理，且与 `matchLog` 的
   「lowercase 后子串匹配」语义严格一致（两侧同用 `.toLowerCase()`，不会出现
   「匹配了但没高亮」的错位）。
2. **大小写折叠只用于定位，切片取原文**——高亮不改变作者写的任何字符。
3. **窗口边界不变量**：片段切片后按整段 needle 做 `indexOf`，恰好被切口截断的命中
   （needle 跨越窗口边界）不会被标出——截断串不可能等于完整 needle，天然不会产生
   「半个词被高亮」的残段。测试里钉一条边界用例。

页面接线（`src/app/logs/page.tsx`，RSC 内联渲染）：

```tsx
{/* title：全量高亮 */}
{highlightSegments(log.title, qFilter).map((seg, i) =>
  seg.match ? <mark key={i}>{seg.text}</mark> : <span key={i}>{seg.text}</span>,
)}
{/* before/after 片段行：仅命中字段展示 */}
{snippetRow("BEFORE", log.beforeContent)}
{snippetRow("AFTER", log.afterContent ?? "")}
```

（`snippetRow` 为页内局部函数：`extractSnippet` 得 null 即不渲染；非空则渲染
`{leadingEllipsis && "…"}<片段段>{trailingEllipsis && "…"}`。）

### 1.5 防 XSS 考虑（三层，缺一不可）

1. **结构层（主防线）**：`Segment.text` 一律作为 React 文本子节点渲染。React 对字符串
   子节点默认 HTML 转义——正文里的 `<script>`、`<img onerror=…>` 在列表里就是可见文字，
   不产生任何节点。**全链路不出现 `dangerouslySetInnerHTML`**（grep 验收）。
2. **输入层**：查询词 `q` 只参与 `indexOf` 匹配与 React 文本渲染，永不进入 HTML 字符串拼接、
   永不进正则构造、永不进 attribute（`defaultValue` 由 React 属性转义接管，现有代码已如此）。
3. **渲染旁路排查**：片段不经过 `Markdown` 组件（唯一 Markdown 出口），Markdown 语法字符
   （`##`、`**`）在片段里以纯文本原样可见——这是**有意的**（片段是搜索预览，不是排版），
   同时意味着不存在「Markdown → HTML」的注入旁路。rehype-sanitize 的职责范围不变（详情页）。
4. 既有防线不动：CSP（`default-src 'self'`、`object-src 'none'`、生产无 `unsafe-eval`）、
   Proxy 前置守卫、`getSafeLogs` 的 `isPublished` 恒定。

### 1.6 视觉（待裁决）

`<mark>` 是语义标签（读屏可识别「标记/重点」），样式走 globals.css 一条规则（④ 段 +~4 行）。

| 案 | 规则 | 对比度 | 代价 |
|---|---|---|---|
| **A（推荐）** | `mark { background: var(--color-brown); color: var(--background); }` 棕底纸白字 | 5.56:1（D30 已实测，≥AA） | `--brown` 用途从「仅导航当前项」扩到「高亮底色」——**视觉铁律需负责人裁断放行** |
| B（保守） | `mark { background: var(--color-rule); color: var(--color-ink); }` 暖灰底墨字 | ~11.8:1 | 零新色值决策，铁律一字不动；但高亮偏淡，搜索预览的「命中感」弱 |

推荐 A：高亮的第一职责是「让读者一眼看见命中位置」，棕底在暖纸背景上对比最强；
这与 B1 引入 `--brown` 的初衷（全站唯一强调色）同向。**待裁决**。

## 二、功能二：全站数据导出

### 2.1 触发与链路

- 后台概览页 `/admin` 现有 `[ 从 GitHub 同步 ]`（`form action={syncGithubAction}` +
  `SubmitButton` + `?synced/skipped` 横幅）——导出按钮同位置并排，样式沿用现有边框按钮。
- 新增 Server Action `src/app/admin/export-actions.ts`（`"use server"`）：
  `requireAdminSession()` 起手 → 查库 → 组装 → **返回 `Response`**（不是 redirect）。
- 下载触发用**客户端组件** `src/components/ExportButton.tsx`（`"use client"`）：
  `useTransition` 内直接调用 action → `response.ok` → `response.blob()` →
  `URL.createObjectURL` → 隐藏 `<a download>` 点击 → `revokeObjectURL`；
  进行中按钮换文案「导出中…」（沿用 SubmitButton 的禁用防连点语义）。
- **不用 form action 直返 Response 的替代案**：Next 对 form action 返回 Response 的
  浏览器行为跨版本有差异（导航语义），blob 处理也不显式；客户端组件方案可预测、可测。

### 2.2 数据范围与 payload（新增纯函数 `src/lib/export.ts`）

```ts
// 纯函数：接收 plain objects，返回 plain object——node --test 直测，Action 层只做查库与响应
export function buildExportPayload(input: {
  projects: Project[]; logs: Log[]; handle: string; exportedAt: Date;
}): ExportPayload;

type ExportPayload = {
  meta: {
    app: string; version: string; exportedAt: string; // ISO
    counts: { projects: number; logs: number; published: number; drafts: number };
  };
  user: { handle: string };
  projects: Project[];  // 全字段，按 slug 升序（确定性）
  logs: Log[];          // 全字段（含草稿、contentHash、publishedAt、sourceCommitSha、isAiAssisted），
                        // 按 beforeDate 降序——与大厅排序口径一致
};
```

- **含草稿**：导出是备份语义，本人草稿一并导出；与「前台不可见」是两件事（后台本就可见）。
- **全字段**：不设 select 白名单（用户点名「包含所有字段及内容」）；Project/Log 两表均无
  凭据字段，导出面天然不含 `User.githubAccessToken`（根本不查 User 表）。
- 排序确定性进纯函数（测试钉住），避免导出文件内容随查询顺序漂移。

### 2.3 安全与合规

1. `requireAdminSession()` 第一行（三处判定共用入口，D21）；数据层 `where: { userId }`
   复合条件，跨租户读不到（0 行即不存在，DAL 口径）。
2. 文件名 `laity-export-<YYYY-MM-DD>.json`：静态前缀 + 服务端日期，**无任何用户输入进
   响应头**（消除 CRLF/头注入面）；`Content-Type: application/json; charset=utf-8`。
3. `Content-Disposition: attachment` 触发下载；响应大小不受 `bodySizeLimit: "6mb"`
   约束（那是**请求**体上限）；单人规模（数十条日志 × KB 级）无压力。
4. 错误路径：查库异常 try/catch → `redirect("/admin?error=EXPORT_001")`；
   `error-text.ts` 补 `EXPORT_001` 文案；概览横幅经 `errorCodeChip()` 过滤（未知码不回显，D28）。
5. 不新增环境变量、不改 nginx、不改 CSP（同源 fetch，`connect-src 'self'` 已覆盖）。

### 2.4 测试

- `tests/export.test.ts`：payload 字段完备性（Project/Log 每字段存在）、排序确定性、
  counts 统计、`exportedAt` 为 ISO 串、handle 透传。
- 覆盖边界（项目口径）：Action 的查库与 HTTP 层不在 `node --test` 内，靠
  `docs/02-测试记录/` 自测表 + 本人后台实点一次（导出文件落盘、JSON 可解析、字段齐全）。

## 三、新依赖评估：零新增

| 候选 | 裁定 | 理由 |
|---|---|---|
| `archiver`（zip） | **不引入** | ① AGENTS 红线：新增依赖需停批 + 许可证核查 + linux 容器重算锁文件（I018 复发过）；② zip 容器格式（CRC32/本地头/中央目录）手写易错，为单人备份引入格式风险不值；③ JSON 无损（全字段 + 草稿）且可再渲染，可读性缺口可日后基于 JSON 加 Markdown 视图（YAGNI，本轮不做） |
| `jszip` 等其他 zip 库 | **不引入** | 同上 |
| JSON | **采用** | 用户兜底口径；无依赖、无格式风险、字段无损 |

结论：**不新增任何依赖**，`package.json` / lockfile / `licenses.ts` / 四道门禁的依赖面均不动。
