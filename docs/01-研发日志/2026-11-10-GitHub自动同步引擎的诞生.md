## 二、踩坑记录（现象 → 根因 → 修复）

### 坑 1：`encodeURIComponent` 把斜杠吃了，导致 404
- 现象：点击同步按钮，接口返回 `SYNC_002`。终端日志显示 `fetchSyncRepos` 成功拿到了 3 个仓库，但拉取 commits 时全部失败。
- 根因：在拼接 GitHub API URL 时，使用了 `encodeURIComponent(repo)`。而 `repo` 的格式是 `owner/repo`，编码后斜杠变成了 `%2F`。GitHub API 不认 `%2F` 作为路径分隔符，直接返回 404。
- 修复：去掉 `encodeURIComponent`，直接拼路径 `/repos/${repo}/commits`。

### 坑 2：权限不足导致的 404
- 现象：授权登录后，拉取 Commit 仍然失败。
- 根因：一开始的 OAuth App 只申请了 `read:user` 权限。GitHub 要求读取仓库的 Commit 必须有 `public_repo` 权限。
- 修复：在 `auth.ts` 的 `GitHubProvider` 中补充 `public_repo` scope，用户必须去 GitHub 撤销授权后重新登录。

### 坑 3：`?? null` 把去重锚点清空了
- 现象：同步草稿在编辑页保存后，再次点击同步，会生成重复的草稿。
- 根因：表单保存时，`sourceCommitSha` 是未定义的。代码里写的是 `sourceCommitSha: input.sourceCommitSha ?? null`，直接把它覆盖成 `null`，导致去重失效。
- 修复：使用条件展开 `...(input.sourceCommitSha !== undefined && { sourceCommitSha: input.sourceCommitSha })`，避免把去重锚点洗掉。

## 三、今日结论
对接第三方 API 时，永远不要相信“我以为”。URL 编码规则、最小权限 scope、表单反序列化时的空值覆盖，这三者简直是 API 对接的“三座大山”。最终实测：102 条 Commit 经过滤合并后生成了 12 条草稿（`synced=12`）。
