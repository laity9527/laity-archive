## 二、踩坑记录（现象 → 根因 → 修复）

### 坑 1：`user.login` 不存在，认领逻辑静默失效
- 现象：本地配置好 GitHub OAuth 后，点击授权，页面 302 跳回了 `/login`，无法进入 `/admin`。
- 根因：NextAuth v4 的 `jwt` 回调中，`user` 对象是被归一化过的（只含 id/name/email/image），并不包含 GitHub 的登录名。真正的原始资料在独立的 `profile` 参数里。代码里去读 `user.login` 恒为 `undefined`，导致认领逻辑被 `if` 静默跳过。
- 修复：改从 `profile.login` 读取；并加 `try/catch` 打印错误日志后原样上抛，杜绝静默失败。

### 坑 2：旧账号认领失败，多建了一个空号
- 现象：认领逻辑修好后，登录成功，但后台空空如也，那 12 篇真实日志不见了。
- 根因：我的 GitHub 账号名是 `laity9527`，但原本 V1.0 数据库里的用户 `handle` 是 `zhanglei`。认领链路按 `handle` 匹配不上，于是自动新建了一个空账号。
- 修复：在生产库手动执行 SQL，将旧号的数据 `UPDATE` 过户给新号，并删除旧号。

### 坑 3：复合唯一键导致所有 `where: { slug }` 报错
- 现象：迁移完成后，跑 `tsc` 报了一堆错误，提示 `where: { slug }` 不符合类型。
- 根因：多租户下，`slug` 不再是全局唯一的，我们改成了 `@@unique([userId, slug])`。因此 Prisma 要求必须使用 `userId_slug` 复合键进行查询。
- 修复：全面改写数据访问层，所有查询替换为 `where: { userId_slug: { userId, slug } }`，或者在 `findFirst` 中使用字面量 `where: { userId, slug }`。

## 三、今日结论
多租户改造不仅是数据层的 `userId` 注入，它像水波一样牵动了路由体系（全站迁移到 `/u/[handle]` ）、鉴权守卫（Proxy 判 `userId`）和查库方式。只要有一处遗漏，就会引发水平越权（IDOR）风险。
