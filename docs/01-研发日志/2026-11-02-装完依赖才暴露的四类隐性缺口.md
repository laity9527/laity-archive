## 二、原以为的差距 vs 实际的差距

我原来的判断是：5b 就差装个依赖，装完就能验。跑下来发现"装依赖"这一步本身带出三件谁都没预料到的事：

- 装包动作把我十几天前刚修好的 lockfile 跨平台同步**又破坏了一次**；
- 依赖装上了，构建反而是红的，而 lint 和类型检查全绿；
- 生产那半套（变量模板 + 编排透传）根本不存在，而本机永远测不出来。

结论是：**"能装依赖"不等于"能上线"**。这三件事没有一件能靠读代码看出来，全都是跑出来的。

## 三、踩坑记录（现象 → 根因 → 处置）

### 坑 1：装包把 linux 才需要的依赖边剪掉了

- 现象：装完 `ali-oss` 后，容器内 `npm ci --dry-run` 报 `Missing: @emnapi/runtime@1.11.3 from lock file`。这正是 I018 十几天前修过的那条。
- 根因：Windows 本机 `npm install` 会按当前平台重算可选依赖，把 linux/wasm32 用到的 `@emnapi/core`、`@emnapi/runtime` 四条边从 lockfile 里剪掉。本机装包动作本身就是破坏动作，不是无害动作。
- 处置：在 `node:24-slim` 容器里 `npm install --package-lock-only` 重算，四条边原样加回来，0 删除、0 版本变化、来源仍是 npmmirror；容器与本机两侧 `npm ci --dry-run` 都退出 0。今天还顺带把这修复端到端验穿了——Phase 6 镜像的 deps 阶段真跑 `npm ci` 通过。
- **流程加一条**：以后凡是本机装包，必须在 linux 容器重算一次 lockfile，而不是"在容器里验一次"就完事。

### 坑 2：lint 与 tsc 全绿，build 却是红的

- 现象：`npm run build` 报 `./node_modules/urllib/lib/detect_proxy_agent.js:24:44 Module not found: Can't resolve 'proxy-agent'`，导入链一路追到 `src/lib/oss.ts`。
- 根因：`urllib@2` 用懒加载 `require('proxy-agent')`，这个包本就不在新增的 68 个包里（只有设了代理环境变量才会真用到）。Next 会把 Server Component 用到的依赖打进 bundle，Turbopack 静态解析这句 require 时找不到模块就判失败。
- 处置：`next.config.ts` 加 `serverExternalPackages: ["ali-oss"]`，让它不进打包、运行时用原生 require。改完不是"应该没问题"就交出去：本地产物里有 `ali-oss`（599K）、`docker build --target runner` 出图成功、镜像内 `require('ali-oss')` 和客户端实例化都通过，`proxy-agent` 缺席也不报错。**外部包 + standalone 是容易漏文件的组合，只验 build 不够。**
- 记一句：类型检查绿灯 ≠ 构建绿灯。

### 坑 3：生产侧的 OSS 变量整段不存在

- 现象：我把"需要换成真实值的东西"列清单时顺手 grep 了一遍 `OSS`，在 `.env.production.example`、`docker-compose.prod.yml`、`Dockerfile`、`nginx.conf` 里**零命中**。
- 根因：5b 只改了开发侧模板 `.env.example`；生产编排的 `app.environment` 也没有这四个键。而 `src/lib/oss.ts` 的 `requireEnv` 缺键就抛错。本机走 `.env` 直连，所以这个缺口在本机不可见。
- 处置：模板补四行、编排补四行，都用 `${VAR:?}` 把失败提前到部署阶段；preflight 也补了同四条判定。这里还纠正了我自己一个说法——我原以为 preflight 会比 compose 插值更早失败，实测相反：把 `OSS_REGION` 置空后 `docker compose up` 直接退出 1，插值就拦住了，**一个容器都没起**。所以 preflight 那四条的价值是门禁清单自证和兜底，不是第一道防线，我把这句写进文件头注释，免得以后有人当它是主门禁。

### 坑 4：工具和探针自报的数字不能直接信

今天三次被自己的探针坑到：

- 把 `head -12` 接在 `npm ci` 后面读退出码，得到"红"，实际是被截管道造成的假红，完整跑完是 0；
- 计数脚本里对已经是数字的结果又取了一次 `.length`，打印出一串 `undefined`；
- 把路径当文件内容去 `split`，得出"页块数 0"这种荒唐数。

还有一条属于另一类：DESIGN 里 5b 的批准记录写着"直接依赖含 lodash、urllib@2、xml2js、ws、socks 等"，`npm install --dry-run` 当时估的 68 个包也对得上，但实际锁文件里**没有 `ws`、也没有 `socks`**。数量相等不代表集合相同，预估清单必须逐个探存在性。

另外 Windows + Git Bash 的老坑又出现两次：`docker run -w /w` 被改成 `W:/`、`openssl req -subj "/CN=..."` 被当成路径。都要 `MSYS_NO_PATHCONV=1`。

### 坑 5：预跑整套编排扒出来的两条新账

- I025：`docker compose run --rm migrate db seed` 跑不起来，加 `--build` 也一样报 `@prisma/client did not initialize yet`。根因是 deps/migrator 阶段只做 `npm ci`，`prisma generate` 只在 builder 阶段执行，镜像里的 `.prisma/client` 还是抛错的桩。迁移本身不受影响（今天 `migrate deploy` 成功）。我倾向把 seed 定为"本地开发的伴生动作"，生产数据一律后台录入，而不是把 generate 塞进 migrator 让镜像变肥。
- I026：本机 `laity-archive-migrate:prod` 是 10-30 09:55 的旧镜像，`command -v openssl` 在里面找不到；同一天我用 `docker build --target migrator` 新构建的镜像里 `/usr/bin/openssl` 是有的。`docker compose build migrate` 连跑两次、`run --build` 都跑过，镜像 ID 一直是 `4b925be03f65` 没换。**为什么 compose 认为它已经最新，我没查明白，这里不下结论。**能确定的是危险：服务器上照 `build && run --rm migrate` 走，迁移可能静默跑在旧镜像里。6b 之前的临时招是迁移后比对 `docker images -q` 的 ID，别只信命令返回 0。

## 五、沉淀成规矩的三条

1. 本机装依赖 = 破坏性动作：装完必须在 linux 容器重算 lockfile，并两侧各跑一次 `npm ci`。
2. 验收档位要分三层：静态检查绿 → 构建绿 → 产物内运行时绿。只到第一层就说"通过"，是把"没报错"当"能跑"。
3. 任何工具、脚本、文档自报的统计数字，先抽几条对拍原始数据再用；预估清单要逐条探存在性。

## 六、晚间补记：全仓库双轴审查又翻出四件事

白天以为 5b 收尾了，晚上让助手把整个仓库按"标准轴 + 规格轴"审了一遍，结果比白天那一轮更值钱。

### 一、最要命的一条不是代码，是我自己造成的

两个被 git 跟踪的模板文件 `.env.example` 与 `.env.production.example` 被我填进了真实凭据——我照着"哪些文件需要换成真实值"的清单去填，结果把值填进了**模板**而不只是本地 `.env`。仓库历史是干净的（扫了 19 个 commit 的四个相关 blob，密钥键全是空），origin 还落后三个 commit 没推出去，等于网络故障替我挡了一次事故。

真正让我后背发凉的是传播路径：软著生成脚本的收录清单里有 `.env.example`，**只要我再跑一次生成，密钥就被印进要提交的 PDF 材料**。清回空值之后，我没有直接相信"扫描无命中"这句话——第一版探针按物理行取文本，报出"长度 811"的假阳性；改成按 `<div class="ln">` 行节点取，再拿一行合成的假值做对照，确认它抓得到非空值，才敢承认这次"干净"成立。

### 二、SPEC 里写着的能力，实际上根本达不到

`server-actions.md:83` 写明 Server Action 请求体默认 1MB，而我这边 SPEC 与代码都按 ≤5MB 设计。也就是说：**任何超过 1MB 的图在进 `uploadImage()` 之前就被框架拒了，还不会映射成 IMG_001**。这条从 Phase 5b 第一天起就存在，lint/tsc/build/镜像全部通过，没有人发现。抬到 `experimental.serverActions.bodySizeLimit: "6mb"` 之后才对得上——我第一次写成顶层键，`tsc` 立刻报 TS2353 把我拽回来。

同一批还翻出 `unpublishLog`：SPEC:117 定义得好好的，`src/` 里 grep 零命中，而且**之前一直没挂账**。这属于"规格有、代码无、台账也没有"的三不管地带，比挂账的坑更危险。

### 三、代理的话不能原样用

两条它说重了我没采纳：把 `publishLog` 判成"存证非原子"——实际上三个字段写在同一条 UPDATE 里，AGENTS.md 的要求是满足的，剩下的只是读-改-写竞态；说 nginx 的 6m"无用"——抬升动作上限后它仍是第一道兜底。另有一条它引的官方文档句子在我查的文件里根本不存在，我改查 `instant.md` 才拿到权威表述：`instant = false` 是退出即时导航校验，**不是**"把页面变成动态路由"，我们的注释一直描述错了，用法是对的。

结论是：代理适合做覆盖面，不适合做结论。九处注释、五个 `pickParam`、两处哈希口径这些是它找到、我逐条 grep 核实之后才动手的。

### 四、三个我自己写错、被工具当场抓住的地方

- 把「下架」表单插进了 `{!log.isPublished && (...)}` 的内部——锚点找的是"发布表单末尾"却没注意外层被条件包着，`tsc` 报 TS1005。**改 JSX 必须先看清外层括号的归属**。
- `getArchiveBoard` 排序后用解构丢字段，eslint 报 unused，改成显式重映射。
- 台账批量改状态列时多补一个竖线，四行从 6 列变 7 列——`awk` 数一遍列数才暴露， markdown 表格坏在渲染前是看不见的。

还有一次 `taskkill` 和查库串成一条命令被安全策略拦下，拆成两条就正常：**链式命令里混一个高危动作，会把无害的验证一起拖死**。后台任务 `TaskStop` 之后 `next start` 子进程仍占着端口（I008 的老坑第二次复现），先 `Get-CimInstance` 核对命令行确实是本仓库那个进程，再定点杀。
