## 二、踩坑记录（现象 → 根因 → 修复）

### 坑 1：GitHub Actions 拉取代码的 443 超时
- **现象**：自动部署工作流跑通了 SSH 连接，但执行 `git fetch` 时连续三次超时报错（`Failed to connect to github.com port 443`），触发防呆中止。
- **根因**：国内服务器直连 GitHub 拉取代码网络极其不稳定。
- **修复**：彻底改变部署策略，放弃让服务器 `git pull`，改用 `appleboy/scp-action`。由 GitHub Actions 把打包好的代码直接推到服务器，彻底绕开服务器访问 GitHub 的网络问题。

### 坑 2：SSH 指纹校验永远 `mismatch`
- **现象**：在部署脚本中配置了 `DEPLOY_SSH_FINGERPRINT` 用于校验服务器指纹。但无论怎么重新生成 `SHA256` 字符串，`drone-ssh` 始终报 `host key fingerprint mismatch`。
- **根因**：由于阿里云的多层网关/负载均衡，在 GitHub 侧拿到的实际 Host Key 与我们在服务器上直连获取的并不一致（或者存在算法协商错位）。在这个单人项目、且已配置私钥登录的前提下，死磕指纹校验 ROI 极低。
- **修复**：永久移除 `fingerprint` 校验，依赖私钥认证与 HTTPS 保护链路。

### 坑 3：GET 表单搜索丢失筛选参数
- **现象**：在日志大厅加上 `<form method="get">` 后，如果当前已经按“项目”筛选，再输入关键词搜索，原有的项目筛选参数会丢失。
- **根因**：原生的 GET 表单提交会覆盖当前 URL 的所有参数，而不是追加。
- **修复**：在搜索表单里加上隐藏的 `input`（`name="project"` 和 `name="tag"`），携带当前的筛选值。并在链接生成函数 `logsHref` 中确保 `q` 参数也被透传。

## 三、今日结论
今天的两项功能都极大地提升了系统的上限。GitHub Actions 的闭环意味着“代码推上云端即上线”，彻底解放了双手。而全局搜索采用内存过滤（因为首页本来就全量加载了数据），在不增加数据库负担的前提下实现了对 `title`、`beforeContent`、`afterContent` 和 `tags` 的全覆盖模糊搜索。
