# 2026-11-11 研发日志：从手工作坊到 SaaS 工厂——Laity V2.0 架构演进复盘

作者：张磊
日期：2026-11-11
背景：V2.0 的主体工程到今天正式落幕。回头再看，这十来天不是"加了几个功能"，而是把一套只服务我一个人的手工作坊，改造成了一套任何 GitHub 用户登录进来都能各用各的、互不越权的 SaaS 工厂。这篇日志不记流水账，只记两件事：架构是怎么一层层演进的，以及那些差点让我翻车、最后逼着我改掉坏习惯的坑。

---

## 一、为什么叫"手工作坊到 SaaS 工厂"

V1.0 的 Laity 本质上是个手工作坊：全站只有我一个管理员，登录靠一个写死在环境变量里的 `ADMIN_PASSWORD`（决策 D20），数据表里没有"这是谁的"这个概念——因为根本不需要，所有东西都是我的。它够用，但它有个致命的天花板：**这套系统只能有一个主人**。

V2.0 要做的，是把这个天花板拆掉。拆掉之后我才发现，"多一个用户"从来不是加一个字段那么简单，它像水波一样往外扩：

- 鉴权要换：口令登录退役，恢复 GitHub OAuth（D33 取代 D20），每个账号凭自己的 GitHub 身份进来。
- 数据要隔离：`Project` / `Log` 全部挂上 `userId`，slug 从全局唯一改成租户内唯一 `@@unique([userId, slug])`。
- 路由要搬家：访客侧从 `/logs/[slug]` 整体迁到 `/u/[handle]/logs/[slug]`，每个租户有自己的主页。
- 写入要设防：所有 Server Action 与数据访问层强制带 `userId` 复合条件，杜绝水平越权（IDOR）。
- 留痕要自动：GitHub 同步引擎把公开 commit 拉成草稿，AI 再把草稿写成可读的复盘初稿。

这四层叠起来，才叫"工厂"——流水线上的每一道工序都认得"这是哪个租户的料"，而不是默认"反正都是老板的"。

## 二、架构演进的四次跃迁

**第一跃：身份。** 从"一个口令"到"一个 GitHub 身份"。这一步最反直觉的地方在于，它不是换个登录框，而是把"我是谁"这件事从环境变量搬进了数据库的 `User` 表，并且让会话里带上 `userId`。前置守卫 `src/proxy.ts` 从此判的不是"有没有登录"，而是"会话里有没有一个合法的 userId"。

**第二跃：隔离。** 这是工程量最大、也最容易留后门的一跃。我把所有写操作改成 `updateMany / deleteMany({ where: { id, userId } })`，命中 0 行就报 `LOG_002 / PRJ_004`——别人的资源和不存在资源，对外表现完全一致，不泄露"这条数据存在但不属于你"。读路径同理，公开查询封装在 `src/lib/logs.ts` 里强制 `isPublished: true` 加租户条件。这一跃教会我：**隔离不是在某一个入口加判断，而是在每一条通往数据库的路上都加判断**，漏一条就是越权。

**第三跃：自动化。** GitHub 同步引擎（Step 5）。登录时截获 access_token，用 AES-256-GCM 加密落库（`ENCRYPTION_KEY`），token 不进 JWT、不进 session。点同步拉公开仓库的 commit，四道过滤（去 merge、去无意义短消息、按 sha 去重、同仓库同日合并）后生成草稿，`sourceCommitSha` 做幂等锚点。实测 102 条 commit 过滤合并成 12 条草稿。

**第四跃：AI 辅助。** Step 6 把"写复盘"这件事也半自动化了。编辑器里一个 `[ AI 帮我写 ]` 按钮，手动触发，把 commit 列表交给国内合规大模型（OpenAI 兼容协议，默认 DashScope / qwen-plus），生成 BEFORE/AFTER 初稿回填。三条边界焊死：单次最多 12 条 commit（超了报 `AI_002`）、失败统一降级 `AI_001` 且不阻塞保存发布、生成内容落 `isAiAssisted` 标记并在详情页打 `[ AI 辅助生成 · 作者审校 ]` 标签。**AI 写的是初稿，作者审校才是存证语义**——这条底线我没让。

## 三、踩坑复盘：那些逼我改坏习惯的瞬间

下面这几个坑，单看都是小问题，但它们有个共同点：**全都源于"我以为"**。我以为 URL 该编码、我以为文件参数是 File、我以为 user 对象里有 login、我以为改 schema 随时能迁移。每一个"我以为"都被现实打了一巴掌。

### 坑 1：`encodeURIComponent` 把斜杠吃了，GitHub 直接 404

- 现象：点同步按钮，`fetchSyncRepos` 明明拿到了仓库列表，但逐仓库拉 commit 全部失败，横幅报 `SYNC_002`。
- 根因：拼 GitHub API 路径时我写了 `encodeURIComponent(repo)`。`repo` 的形态是 `owner/name`，编码后斜杠变成 `%2F`，整段成了 `owner%2Fname`。GitHub 不把 `%2F` 当路径分隔符，于是 `/repos/owner%2Fname/commits` 命中了一个不存在的资源，返回 404。
- 修复：去掉编码，直接拼 `/repos/${repo}/commits`（见 `src/lib/github-sync.ts:122`）。
- 反思：`encodeURIComponent` 是给"查询参数的值"用的，不是给"路径段"用的。把一个本身就含合法路径分隔符的字符串整体编码，等于亲手把路径结构毁掉。**对接第三方 API，URL 的每一段是路径还是参数，必须分清楚，不能一把梭全编码。**

### 坑 2：FormData 的两个陷阱——跨边界的 Blob，与受控组件的取数口径

这个坑我栽了两次，分别在不同的层。

**第一次：文件参数跨 RSC 边界后不是 File。** 图片上传的 Server Action 里，我写了 `if (!(file instanceof File))` 来校验。结果真实上传一律被拒成 `IMG_001`，连一张 70 字节的合法 PNG 都过不去。根因是：表单里的文件参数穿过 React Server Action 的序列化边界后，到达服务端时实体是 **Blob 而不是 File**——`File extends Blob`，但反序列化重建出来的是 Blob，`instanceof File` 恒为 false。修复是改判 `instanceof Blob` 并显式拒零字节（`src/app/admin/upload-action.ts:36`）。教训：**跨运行时边界的东西，类型会退化，不能拿浏览器里的 instanceof 经验直接套到服务端。**

**第二次：AI 按钮取数，必须走表单序列化。** 编辑器是双栏受控组件，BEFORE/AFTER 两个 textarea 同一时刻只有一个可见（另一个 `hidden`）。点 `[ AI 帮我写 ]` 时，如果我手工去拼"当前页签的 state + 标题"，很容易漏掉隐藏页签里的内容，或者拿到与 DOM 不同步的闭包快照。最终口径统一成 `new FormData(form)`：它直接从 DOM 序列化出这张表单**真正会被提交的全部字段**——标题、两个正文（无论可见与否）、隐藏标记，一个不漏。教训：**取数的唯一可信来源是"表单实际会提交什么"，而不是"我脑子里以为表单里有什么"。** 这也顺带解释了为什么 `isAiAssisted` 要做成隐藏域随表单走——它得和正文一起被序列化、一起落库，而不是靠某个组件单独记得它。

### 坑 3：NextAuth 的 `user` 里没有 login，认领静默失效

- 现象：配好 GitHub OAuth，点授权，页面 302 跳回 `/login`，进不了后台。
- 根因：NextAuth v4 的 `jwt` 回调里，`user` 是被 `provider.profile()` 归一化过的对象，只有 `{id, name, email, image}`，**没有 login**。GitHub 的原始资料（含 login）在独立的 `profile` 参数里。我去读 `user.login` 恒为 undefined，认领逻辑被 `if` 静默跳过。
- 修复：改读 `profile.login`，并加 try/catch 落日志后原样上抛，杜绝静默失败（`src/auth.ts:87`）。
- 反思：框架回调里的每个参数都有它的契约，`user` 和 `profile` 长得像但语义不同。**读框架源码确认参数形状，比凭训练记忆猜快得多，也准得多。** 这次我一开始还怀疑是 RFC 9207 的 iss 校验问题，查了源码才发现 issuer 早已是默认值——假设错了方向，白绕一圈。

### 坑 4：Windows 下 Prisma 引擎 DLL 被 dev server 锁死（EPERM）

- 现象：改完 `schema.prisma` 跑 `npx prisma migrate dev`，报 `EPERM: operation not permitted, rename ...query_engine-windows.dll.node`。
- 根因：本地 Next dev server 还在后台跑，它加载着 Prisma 查询引擎 DLL。Windows 不允许覆盖正被进程占用的文件。
- 修复：先停 dev server，再迁移。
- 反思：这个坑在 Linux 上根本不存在（可以覆盖已打开的文件），是 Windows 特有的文件锁语义。**环境差异不是"差不多"，是会在某个具体操作上突然咬你一口的东西。** 以后改库结构，先关本地服务，已成肌肉记忆。

### 坑 5（顺手记）：`?? null` 把去重锚点洗掉了

同步草稿编辑保存后再点同步会重复产草稿。根因是表单保存时 `sourceCommitSha` 未定义，`input.sourceCommitSha ?? null` 把它覆盖成 null，幂等锚点失效。修复用条件展开，只在显式提供时才写入。**空值合并是个好习惯，但用在"可选锚点字段"上会把锚点本身抹掉——要区分"没填"和"要清空"。**

## 四、真正沉淀下来的工程纪律

坑踩多了，会发现它们背后是同一套纪律在起作用。这套纪律比任何单个修复都值钱：

1. **四道门禁全 0 才算数。** lint / tsc / build / test，每一道都跑真实输出，不用"看起来没问题"替代。这次 AI 接入我就被 lint 抓到一个 `useEffect` 依赖数组漏项（新加的 `aiAssisted` 没进依赖），被 tsc 抓到 Prisma 客户端类型没重生成——都是机器先于我发现的。

2. **软著材料窗口交给机器判，不靠人估。** `assertWindowFit()` 按折行后的真实行数检查 1500 行窗口，任何一次普通改动（哪怕加两行注释）都可能顶破窗口。这次加 `isAiAssisted` 字段、加 AI 隐藏域，都是先跑生成器看护栏放不放行，再决定要不要平移文件。**"看着装得下"和"实际装得下"是两回事，第八、九轮都是这么翻车的。**

3. **单一来源，改一处跟着改一处。** 错误文案集中在 `error-text.ts`，环境变量集中在 AGENTS 总表 + 两份 `.env*.example` + compose 透传，摘要口径只有 `content-hash.ts` 一份实现。多租户改造之所以没失控，靠的就是"每件事只有一个权威出处"。

4. **范围外的问题记台账，不动手。** ISSUES.md 里那些 OPEN 项，是"发现了但本轮不该碰"的事。克制住顺手重构的冲动，才能保证每一轮 commit 的边界干净、可回滚。

5. **未实测就如实标未验证。** 数据库层、需登录的 Server Action、页面渲染不在纯逻辑单测覆盖内，那部分靠自测表与人工联调。我不用"测试全绿"冒充"功能全通"。

## 五、结语

从手工作坊到 SaaS 工厂，Laity 这十来天走完的路，恰好是一个个人项目走向"可被他人使用"必须走的路：身份、隔离、自动化、辅助生成，一层叠一层。而真正让我成长的不是这些功能本身，是那些坑逼着我承认的一件事——**我对框架、对运行时边界、对操作系统、对第三方 API 的"以为"，绝大多数时候都靠不住。** 唯一靠得住的，是读源码、跑真实输出、让机器当护栏，以及把每一次"我以为"被打脸的过程，老老实实记下来。

V2.0 闭环了。但"别信我以为"这条纪律，才刚刚开始。
