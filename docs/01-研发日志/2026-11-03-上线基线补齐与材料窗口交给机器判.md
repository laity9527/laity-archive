## 三、踩坑记录（现象 → 根因 → 处置）

### 坑 1：材料窗口的算术本来就错了

- 现象：I034 是这一天里最难看的一条——50 个收录文件里有 **15 个不在提交页中**，而且缺的偏偏是最能代表软件的那几个：`src/app/page.tsx`、`SiteNav.tsx`、`Editor.tsx`、`StatusBoard.tsx`、`Seal.tsx`、`sitemap.ts`、`robots.ts`。材料形式上仍符合"前 30 页 + 后 30 页"的通用作法，但审查员翻到的全是数据层与工具层。
- 根因：代码量涨上来以后，"前后各 30 页"自然把中间的界面层折走，而我原先按"分段感觉"判断装得下——第八轮按感觉排完，实测仍把 `src/proxy.ts` 折走了 130 行、`globals.css` 整份失踪。
- 处置：收录清单从一条扁平 `ORDER` 改成 `BANDS`（四段，③ 标 `foldable`），并新增 `assertWindowFit()`：非折走段的文件只要被窗口切断或整份掉进折走段，**直接拒绝出件**。

### 坑 2：后窗口容量不是 1500 行

- 现象：第一版 `assertWindowFit()` 按"前后各 1500 行"判，自己通过了，而我拿生成的 HTML 反推才发现 `globals.css` 的头部被切掉。
- 根因：后窗口取"最后 30 个页块"，末页只有 9 行也占一整页名额，所以真实容量是 1459 行（本轮之后又变成 1453/1456 这类数）——**按整页折算，不是固定行数**。
- 处置：判据改成按整页折算的行跨度；并且定下口径：**自研工具自报的窗口结论不能直接采信，要从产物反推再核一遍**（这条今天两次救了我）。

### 坑 3：三行注释就能顶破窗口

- 现象：给 `eslint.config.mjs` 加了三行注释（I039，让 `tmp/**` 不参与 lint），收录的 ①+② 段从 1486 行被顶到 1501 行，`proxy.ts` 又被切掉一行。
- 根因：收录清单的容量是全局耦合的，任何一次"无关改动"都可能把某个关键文件挤出窗口。
- 处置：这类事不该靠人事后对拍。加上坑 2 的修正，判据每次生成都跑；CI 里再加两步——`node tools/软著材料生成.mjs`（完整性 + 窗口）与 `git diff --exit-code -- docs/04-软著材料`（成品与重新生成结果逐字节一致）。

### 坑 4：健康探针到底该判什么

- 现象（I036）：app 容器的探针原本打 `/login`，返回 200 就算健康。可库完全连不上的时候 `/login` 照样 200。
- 根因：`/login` 只证明进程活着、路由通，不证明应用真能取到数。
- 处置：探针改打 `/api/health` 并解析响应体，要求 `db === true` 才退出 0，`start_period` 给到 30s；`web` 改为等 `app` healthy 再起。探针表达式另用桩服务器做了五路自检：真健康退 0，503、返回 HTML、字段缺省、端口无人各退 1——**一个恒返回 0 的探针比没有更坏**。入口网关反而不加探针：80 端口直接 301，busybox wget 对重定向的判定不稳，与其装一个会误报健康的探针，不如没有。代价写清楚：库抖动会把 app 标成 unhealthy，但 compose 不因 unhealthy 自动重启、`depends_on` 只在启动时把关，不会级联停摆。

### 坑 5：想验证"构建期会不会查库"，被策略拦下三次

- 现象：为了决定 CI 要不要配数据库，我让本机停掉共享容器做实验，安全策略连拦三次（停共享容器、打印带口令的连接串各算一类），我没有换写法绕。
- 处置：既然结论拿不到，就不要拿"赌"当设计依据——CI 直接配一次性 `postgres:16` 服务，`prisma migrate deploy` 与 `npm ci` 都跑在它上面。这样两种情况都成立，顺带把 I018 那类"Windows 安装把 linux 平台条目从锁文件里剪掉"的问题变成常驻防线。工作流里的 env 全是显眼的占位值，不含任何真实凭据。

### 坑 6：GitHub 授权第一次实走就撞墙

- 现象：15:15 本机第一次真点了一次登录。`/login` 页本身正常，点"用 GITHUB 登录"后落到 `github.com/login/oauth/authorize?...`，GitHub 返回 404 页。
- 处置（当天只做到定位）：对本地 `.env` 只做派生判定、不回显值——`GITHUB_ID` 长度 20 且**含大写字母**，而 GitHub 的 client ID 全为小写，所以判为手抄/OCR 失真而不是 OAuth App 被删；`NEXTAUTH_URL` 经同法核实等于开发地址 `http://localhost:3000`，说明拼出的回调地址本身是对的。结论是问题只落在一个值上。排障行与台账状态是次日早上才成文的（`8d909fa`），今天没写成文档，这条缺口记在这里。
