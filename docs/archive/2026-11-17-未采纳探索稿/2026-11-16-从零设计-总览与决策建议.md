## 零、一句话结论

**"从 0 开始"这次推演的价值，不在于它比 V3 好看，而在于它把一个被藏起来的问题摆到了台面上：这个站的可信度到底靠什么承载？**

V3 的答案是"靠材质"——纸白、墨色、宋体、印章、克制本身构成Archive感。
探索方案的答案是"靠读数"——发布时间、内容摘要、提交来源同屏可核，读者不必先接受任何隐喻。

工程侧给出了一个诚实到近乎扫兴的判断：**如果目标只是"更美观"，不要启动这个方案。** V3 的边际成本已接近 0，而本方案要重绘 18 个图标、重写打印、拆 540 行 CSS、制造文档口径分叉，换来的视觉差异不足以抵消。只有当"核验"真正成为产品 KPI 时，它才值得。

## 三、三个视觉方向（一句话版）

| 方向 | 隐喻 | 色系 | 最大优点 | 最大风险 |
|---|---|---|---|---|
| 2.1 活字校样 | 印刷品 | 冷灰 `#E8E8E2` + 朱红过印 `#A33228` | 与档案调性亲缘，接受成本低 | 与 V3 太近，会被读成"小改" |
| **2.2 校验台（推荐）** | 仪器 | 石墨黑 `#0C1014` + 磷光青 `#5BD6C4` | 唯一把证据当数据而非陈设的方向 | 做成霓虹赛博或后台面板 |
| 2.3 暗厅陈列 | 展厅 | 暖黑 `#111110` + 黄铜 `#D6B273` | 视觉最有记忆点 | 信息密度最低，长日志易疲劳 |

**推荐 2.2 的理由**：三个方向里只有它把"可信度"从可模仿的材质转移到不可模仿的数据结构上。哈希、UTC 时间、提交来源都是现有字段，不需要新数据，也不碰摘要口径。

## 四、V3 vs 从零：决策对照

| 维度 | V3「克制升级」（已落地） | 从零「校验台」（探索） | 判断 |
|---|---|---|---|
| 设计命题 | 纸墨克制是资产，保留骨相 | 可信度靠读数，不靠材质 | **不同世界观**，不是程度差异 |
| 视觉签名 | 纸白 + 宋体 + 零圆角 + 印章 | 石墨黑 + 无衬线 + 2px 控件 + 三读数 | 不可兼容，必须二选一 |
| 导航 | 4 项（含标签） | 3 项，标签降为 `/logs?view=tags` | 探索方案目的地更少 |
| 发现方式 | ⌘K 命令面板 + 大厅筛选 | 大厅内联 SSR，结果即证据行 | 探索方案更可分享、地址可核对（首屏 JS 不因此变少，见上表） |
| 详情页 | 标题 + 面包屑 + 文末印章 | 标题下三读数，可信度进首屏 | 探索方案把核对动作前置 |
| BEFORE/AFTER | 编号 + 线 + 留白 | Δ 字符差 + 行号刻度 | 探索方案先给量化再给内容 |
| 后台 | 通用管理面 | 发布校验台 + 三段回执 | 两者语义不同 |
| 反馈机制 | 统一 Toast（已落地） | URL 事实 / 就地瞬时 / 后台 Toast 三通道 | 探索方案按语义分工 |
| 打印 | 带走一页文章 | 三读数核对单 + CSS 页码 | 探索方案更贴合存证 |
| 新增依赖 / 数据迁移 | 0 / 0 | 0 / 0 | **打平**，都不是靠堆依赖实现 |
| 回滚难度 | 逐批 revert 基本无损 | 视觉可逆，废弃路由**半可逆**（外链不可回滚） | V3 明显更稳 |
| 边际成本 | 接近 0（已实施 B0–B4） | 大：CSS 全量重排、18 图标重绘、打印重写、口径治理 | **决定性差异** |

## 五、我的建议

### 5.1 如果目的是"让站点更好看"

**执行 V3，不要启动本方案。** 工程侧的结论写得很清楚：本方案换来的视觉差异不足以抵消推翻已验证资产的成本，而且会制造 V3 文档与探索稿长期并存、互相打架的口径分叉。V3 已经在 B0–B4 落地，边际收益高、风险低。

### 5.2 如果目的是"验证核验是不是这个站的真正护城河"

**不要一次性推翻，先做一次最小实验。** 只借探索方案的一个组件——**详情页三读数面板**——在现有 V3 页面上做 A/B 对照，不动导航、不动路由、不动色板、不动图标：

1. 在 V3 详情页标题下插入三读数条（UTC 发布时间 / 摘要 64 位 + 复制 / 提交来源或"本地记录"），用现有令牌渲染，不引入磷光青。
2. 观察真实访客是否在首屏完成核对动作，而不是滑到文末看印章。
3. 如果三读数确实被使用，再讨论是否值得为它重构整套视觉语言；如果没有，探索方案可以正式归档。

这个实验的成本是**一个组件 + 一次数据观察**，而不是 7 个批次的全站推翻。它能在不烧掉 V3 的前提下回答那个真正的问题。

### 5.3 需要你点头的三件事

1. **这两套方案的关系**：继续保持"V3 执行稿 + 探索稿并列"，还是把探索稿标记为"未采纳归档"？我建议后者，并在 V3 总览与三份附录顶部加一行说明，避免后来者按两套数字验收。
2. **是否做 5.2 的三读数 A/B 实验**：我建议做，它是当前信息量最大、成本最低的一步。
3. **工作区未提交改动怎么处置**：当前 `git status` 有 7 个代码文件（含 `CommandPalette.tsx`、`archive/page.tsx`、`lib/*.ts`、`tests/archive.test.ts`）和 5 个文档文件未提交。任何后续动工前都必须先确认这些改动的归属——先 stash 或 commit，否则无论走哪条路都会撞车。

## 七、正确性不变量（两个方案共同遵守）

无论走哪条路，以下不许动：

- `content-hash.ts` 口径：`title + beforeContent + afterContent`
- `userId` 租户隔离与 `@@unique([userId,slug])` / `@@unique([userId,sourceCommitSha])`
- `publish.ts` 的顺序：敏感扫描 → 哈希 → 落库
- 密钥加密，不落库不进日志
- 性能预算：Prisma ≤3/页（`/logs` ≤2）、首屏 JS 增量 ≤15KB gzip、LCP ≤2.0s、CLS ≤0.05、字体首屏 ≤120KB
