## 4. 依赖与性能

| 项 | 评估 | 口径 / 测法 |

| 首屏 JS 净变化 | **净变化约 0，区间 −1~+2KB gzip**（与视觉稿 §2.2「+0~2KB」同向，不再声称净减）。删除侧：`CommandPalette` 本就是 `next/dynamic` 懒加载（`SiteNav.tsx:29–30`），不计入首屏 chunk，删它首屏收益 ≈0；仅 SiteNav 的 ⌘K state/监听消失省约 1KB。新增侧：键盘地图 G15 是新增客户端监听器（`/`、`j/k`、`Enter`、`c`、`←/→`、`n`），若单独成岛约 +1~2KB，视觉稿的 +0~2KB 应已含此项。两侧相抵 ≈0；无论落在哪侧都在 ≤15KB 预算内。不应宣称 −10KB | 对比 `npm run build` 产物 `.next/static/chunks/*.js` 按首屏入口递归依赖求和、gzip 后取差；Lighthouse 移动档 3 次中位数 |
| 字体传输 | **诚实口径：不能预先宣称降 114KB**。114 woff2 / 202 unicode-range 是**构建产物总量**，不是首屏传输量；当前 `preload:false`，首页无 `.log-body` 时首屏可能本就 0 请求。真实收益集中在详情页正文首访 | WebPageTest 分「首页 / 详情页首访」两档实测请求数与传输字节；预算 ≤120KB 两档都要过 |

| Prisma 预算 | 不恶化。三读数全部读现有 `Log` 字段；`/logs?q=` 改为 SSR 需确认仍是 ≤2 次查询 | 在 `src/lib/logs.ts` 取数口临时打点计数，逐页核对 ≤3 / `/logs` ≤2 |

## 5. 批次、完成标准与回滚点

串行主干：**B0 → B1 →（B2 ∥ B3 ∥ B5）→ B4 → B6**。B4 必须在 B2 之后（`logs/page.tsx`、`sitemap-data.ts` 与 B2 同文件）；B2/B3/B5 文件不重叠可并行，但需先完成 §7 的 stash。

| 约束 | 说明 | 违反后果 |
|---|---|---|
| B0 必须最先且单人 | 令牌底座是所有后续批次的公共依赖；样板先给负责人看方向，未确认前不铺开 | 并行改令牌导致冲突，返工覆盖 |
| B1 必须在 B2/B3/B5 前 | 新槽必须先于组件 className 切换存在 | 类名指向未定义变量，样式静默丢失 |
| B2/B3/B5 可并行 | B2 动列表路由、B3 动详情路由、B5 动后台，文件不重叠 | 三者都改 `globals.css` 的补充样式时需约定分段 |
| B4 必须在 B2 后 | 同改 `logs/page.tsx`、`sitemap-data.ts` | 并行删除与改写互相覆盖 |
| B6 必须在最后 | 全量回归与性能验收 | 提前测会漏掉后续批次的退化 |

### 可逆性评估

| 类别 | 内容 | 结论 |
|---|---|---|
| 低成本可逆 | 19 令牌与两套色值、组件视觉、className、18 个图标、三读数/Δ/来源/页码/键盘地图、打印版式、暗色阶梯 | `data-ui` 开关 + revert commit 即可，无数据副作用 |
| 半可逆 | 废弃 `/tags`、`/archive` 的站内代码；删除命令面板 | 代码能 revert；**外链与搜索引擎收录不能回滚**，需长期 301；用户 ⌘K 肌肉记忆不可恢复 |
| 不可逆 / 高成本 | V3 已交付材料与新方向并存造成的口径分叉 | 需显式在 V3 附录标注「探索稿并行、未采纳」；否则两套规格长期互相打架 |
| 本方案为 0 | 数据库 schema 迁移 | 三表、`contentHash` 口径、两个唯一约束全程不动，**不需要任何 migration** |

## 6. 与 V3 工程成本对比

| 维度 | V3（克制升级） | 本方案（从零） | 差值 | 说明 |
|---|---|---|---|---|
| CSS 改动量 | 540 行内局部改，约 50 行 | 拆 4 文件 + 19 槽 ×2 主题，估 700–800 行 | 中→大 | 贵在推翻已验证落地状态 |
| className 改动量 | 视觉稿估约 30 处 | 同量级 30–50 处（全站面 804 处） | 基本持平 | 唯一不更贵的维度；因 tsx 硬编码 hex 为 0，只换令牌名 |
| 组件新增/删除 | 0 | +6 类新组件 +3 图标，−1 命令面板 | 小→中 | 三读数/证据行/Δ/来源/页码/键盘地图 |
| 路由新增/删除 | +3（`/tags` `/archive` `/api/search`） | −3，+2 查询态 | 反向 | 方向相反，不是叠加 |
| 数据迁移 | 0 | **0** | 0 | 关键：两方案都不碰 schema |
| 依赖 | 新增 0 | 新增 0（另减一个字体加载） | 0 | 都能守住 0 运行时依赖 |
| 性能 | 基线 | JS 持平或微降、字体首访收益待实测、列表 DOM 变重 | 小 | 不会突破预算，但也不会白赚 |
| 测试 | 现有 217 断言保持 | 217 不动 + Δ/来源/键盘/打印/301 新增估 25–40 断言 | 小 | 需补 SSR 查询态与 301 的集成测试 |
| 文档与材料 | 已交付 V3 总览 + 附录 A/B/C | 新增视觉/体验/工程 3 份探索稿 + V3 作废声明 | 中 | 口径治理成本常被低估 |
| 回滚难度 | 逐批 revert，基本无损 | 视觉可逆、废弃路由半可逆 | 中 | 301 必须永久保留 |

**诚实结论**：如果只想要「更美观」，这个方向**不值得**——V3 边际成本近 0，本方案要重绘 18 个图标、重写打印、拆 540 行 CSS，并制造 V3 文档口径分叉，换来的视觉差异不足以抵消这些成本。只有当「核验」本身成为产品 KPI（T1–T4 被真实使用、三读数/来源缺失/打印核对单有人用），且团队接受废弃路由外链与 ⌘K 习惯损失时，才值得启动。
