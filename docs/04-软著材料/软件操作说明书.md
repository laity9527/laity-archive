# Laity 项目档案库软件 V1.0 软件操作说明书

著作权人：张磊
开发完成日期：2026-10-30

## 一、软件概述

本软件是一套面向个人全栈开发场景的项目档案库系统，同时承担两项用途：对外作为厂牌作品展示站点，对内作为开发过程与判断依据的存证载体，可用于软件著作权登记后的权属举证与日后维权。

系统由一个面向访客的只读站点和一个按账号隔离的个人控制台构成，二者共用同一套代码与同一个数据库。访客可以浏览首页看板、开发日志与项目档案；完成 GitHub 登录的账号各自进入自己的后台，只能新建与编辑自己的日志、发布自己的日志、维护自己的项目条目，账号之间的数据互相不可见。

软件的核心特征是"发布即存证"：每条日志在发布动作发生时，由服务端先按提交表单保存正文，再按固定口径计算该正文的 SHA-256 摘要并连同服务器时间一并写入数据库，前台详情页据此展示一枚存证印章——盖上的是编辑器里那一份，而不是库里未被覆盖的旧内容。已发布的日志一旦被再次保存，会自动退回草稿状态，原有摘要与发布时间作为历史保留，需重新发布才会按新正文重算，从而保证前台展示的印章与正文内容始终一一对应。

## 二、运行环境

### 2.1 服务端软件环境

- 运行时：Node.js 24（开发与容器构建均使用该主版本）
- 应用框架：Next.js 16.4.3（App Router，Turbopack 构建）
- 语言：TypeScript 5，React 19.3.0
- 样式：Tailwind CSS 4
- 数据访问：Prisma 6.19.3（ORM，provider 固定为 postgresql）
- 数据库：PostgreSQL 16
- 登录鉴权：NextAuth 4.24.15，GitHub OAuth 提供方，会话为签名 JWT
- 包管理：npm
- 容器与反向代理：Docker（镜像构建为多阶段），nginx 1.27
- 图片存储：阿里云对象存储 OSS（外部服务，仅存放日志正文插图，通过 ali-oss 6.23.0 客户端写入）

### 2.2 硬件环境（最低）

- 处理器 1 核、内存 1 GB、磁盘 10 GB 即可运行；构建过程在内存不足时应在构建机或持续集成环境完成，服务器只负责拉取镜像并运行。

### 2.3 客户端环境

- 支持主流现代浏览器（Chrome、Edge、Firefox、Safari 的近年版本）。
- 页面为响应式布局，宽度 375 像素至 1920 像素均无横向滚动。

## 三、安装与部署

### 3.1 开发环境启动

1. 获取源码后执行 `npm install` 安装依赖。
2. 启动数据库：`docker compose up -d`（本地 PostgreSQL 16，端口 5432，库名 laity）。
3. 在仓库根目录创建 `.env` 文件，填入数据库连接串、NextAuth 会话密钥、GitHub OAuth App 的 client id 与 secret，以及对象存储的地域、存储桶名与两把写入密钥。
4. 生成并应用数据表结构：`npx prisma migrate dev`。
5. 启动开发服务：`npm run dev`，浏览器访问 `http://localhost:3000`。

### 3.2 生产环境部署

1. 复制 `.env.production.example` 为 `.env.production`，填写生产数据库用户名与强口令、正式域名、生产会话密钥、GitHub OAuth App 的 client id 与 secret（须为生产域名对应的应用，回调地址为 `https://<正式域名>/api/auth/callback/github`）、对象存储的地域、存储桶名与两把写入密钥（生产建议另建子账号密钥，不与开发环境复用），以及 ICP 备案号。备案号属非敏感信息，未填入时页脚不显示该行。
2. 将 TLS 证书放置于 `deploy/certs/` 目录，并确认 `deploy/nginx.conf` 中的域名与证书路径一致。
3. 构建镜像：`docker compose --env-file .env.production -f docker-compose.prod.yml build`。
4. 应用数据库迁移：`docker compose --env-file .env.production -f docker-compose.prod.yml run --rm migrate`。
5. 启动服务：`docker compose --env-file .env.production -f docker-compose.prod.yml up -d`。
6. 检查：`curl -I https://<正式域名>/logs` 应返回 200，证书受信；`curl https://<正式域名>/api/health` 应返回 `200` 与 `{"status":"ok","db":true}`，数据库不可达时该端点返回 `503` 且 `db:false`。应用容器的健康探针即以该端点的 `db` 字段判定容器健康，因此"容器 healthy"同时代表进程在、路由通、且应用真能连上库；入口网关等应用转为健康之后才启动。

### 3.3 上线前置门禁

编排中设有一次性检查服务，在任何业务容器启动之前校验环境变量：数据库用户名或口令不得为默认弱口令、二者不得相同、数据库口令长度不得少于 12 位、站点地址必须为 https 开头的正式域名且不得指向本机、会话密钥长度不得少于 32 位、GitHub OAuth 的 client id 与 secret 均不得为空。任一条不满足，整个启动流程直接失败，数据库容器不会被拉起。检查通过时仅输出脱敏信息（数据库用户名、数据库口令长度、GitHub 两键非空、域名），不回显任何密钥值。

在上述检查之前，应用容器所需变量已在编排的插值阶段被标记为必填：数据库用户名与口令、站点地址、会话密钥、GitHub OAuth 的 client id 与 secret、对象存储的地域与存储桶名及两把密钥。任一缺失时编排命令在部署阶段即报错退出并指明缺的是哪一项，不会等到用户点击上传时才暴露"缺少环境变量"。

四条门禁另有持续集成流水线在每次提交与合并请求上自动执行，顺序与人工一致，并额外做两项本材料自身的完整性检查：一是源码目录中新增而未被登记进收录清单的文件会直接使流水线失败，二是重新生成一次材料并要求结果与已提交的成品逐字节一致（改了说明正文却忘了重出成品也会被拦）。流水线使用一次性数据库服务容器，其中所有配置值均为占位内容，不含任何真实环境的凭据。

## 四、访客端功能与操作说明

### 4.1 首页

页面顶部为厂牌标语与一句话定位。其下是精选项目区：从已有已发布日志的项目里按最近发布时间取前三条，每条目给出名称、类型、当前状态、日志条数与简介，名称链接到该项目详情页；区头右侧提供"全部作品"文字入口指向项目列表页。尚无已发布日志的项目不进精选区。

再往下是档案状态看板，逐行列出**全部**项目——包括尚未发布任何日志的项目——每行包含状态灯、项目名称、类型、当前状态、日志条数与最近一次记录的日期；没有已发布日志的项目显示"尚未发布"，其条数计为 0，不用创建时间冒充更新时间。状态灯为实心圆点表示项目处于已上线状态，空心圆点表示其他状态；项目名称同样链接到详情页。

最后是最新日志列表，展示最近发布的三条日志，每条左侧为时间轴，右侧为标题与所属项目、标签。

### 4.2 开发日志大厅

访问路径为 `/logs`。页面提供两层筛选：项目维度与标签维度，均以文字链接形式呈现，选中项以下划线标识，未选中项为浅灰色。标签数量超过 12 个时，默认只列出前 12 个，其余收进一个可展开的文字项（点开列出全部、再点收起）；当前选中的标签始终留在默认可见的那一组里，不会出现“正在按某个标签筛却看不见它”。筛选状态通过网址参数传递，可直接分享带筛选条件的链接。列表每行左侧是一条贯穿的细竖线时间轴，标出该条日志的判断时间（BEFORE）与验证时间（AFTER）；右侧是所属项目、日志标题与标签。无匹配结果时显示空状态提示。

### 4.3 日志详情

访问路径为 `/u/<用户名>/logs/<标识>`。正文限宽 720 像素，采用宋体、18 像素字号、1.85 倍行距。页面按顺序展示：所属项目、标题、时间轴、标签，随后是判断阶段（BEFORE）、验证阶段（AFTER）与经验总结三段内容——前两段标题是系统专有术语，按视觉约定以等宽小字呈现，「经验总结」是中文标签，走无衬线小字。段落支持标题、列表、表格、引用、代码块与图片等常见排版。

页面底部为存证印章区块，标注"内容摘要"，其下两行分别是发布时写入的正文摘要与发布时间（均标 UTC 时区），两行的标签是中文、摘要串与时刻按视觉约定仍以等宽字呈现。若该条已发布但库中缺少摘要或发布时间，页面不静默省略印章，而是显示"摘要缺失"告警块并注明"请在后台重新发布一次补齐；缺失期间，本页不构成内容未被篡改的证明"——存证是本软件的核心功能，静默降级比报错更有害。

未发布的日志与不存在的地址一律返回 404 状态码，响应附带禁止索引与禁止缓存标记。

正文的标题层级由书写者用 `#` 的数量决定，但渲染出口把正文里的一级标题降级为二级呈现：本页自己的标题已经是一个一级标题，正文再出一个会让读屏的标题树与搜索引擎面对两个页级标题；各级标题的字号都落在同一套字号阶上，与宋体正文的排版一致。

### 4.4 项目档案

项目列表访问路径为 `/projects`，列出全部项目条目，每行包含状态灯、项目名称、标识与类型、当前状态、简介以及已发布日志条数与最近日期；尚无任何已发布日志的项目同样列出，条数显示为零。

项目详情访问路径为 `/u/<用户名>/projects/<标识>`，顶部展示该项目的标识、类型、状态、名称、简介、起始时间与日志条数，并在配置了仓库地址时提供外链；下方按时间轴列出该项目全部已发布日志，并提供跳转到日志大厅并按本项目筛选的链接。不存在的标识同样返回 404 状态码。

此外，每个账号有一个租户主页 `/u/<用户名>`：顶部显示账号标识，下方复用档案看板（只统计该账号的已发布日志，零日志项目显示"尚未发布"）与最新日志列表；日志详情为 `/u/<用户名>/logs/<标识>`。用户名不存在时返回统一的品牌化 404 页。

### 4.5 站点导航与抓取规则

前台每一页顶部为同一套持久导航：左侧字标指向首页，右侧依次为"开发日志""作品档案""关于"，当前所在项以文字下划线与 `aria-current="page"` 双重标记（当前项的文字与下划线使用全站唯一强调色 `--brown`，非当前项为辅助灰、下划线透明）；后台与登录页不叠加第二层导航。导航首个可聚焦元素是"跳到正文"链接，键盘用户按一次 Tab 即可跳过导航直达正文，正文容器带对应的锚点标识。全站键盘焦点为 2 像素实线，不依赖颜色以外的手段表达状态。

每个页面有独立的标题与描述：列表页使用固定文案，日志详情页的标题即日志标题、描述优先取"经验总结"字段，项目详情页的标题即项目名、描述优先取项目简介。标题统一带站点名后缀模板。

站点提供 `/robots.txt` 与 `/sitemap.xml`：前者放行公开路径并屏蔽后台与登录页，后者在请求期生成，只收录公开路由、全部已发布日志与全部项目，草稿与后台地址在任何抓取文件中都不出现。全站的可交互元素（链接、按钮、输入框）在换色时带 120 毫秒的线性过渡：本站的悬停态是整块反色，零毫秒切换在纸白背景上像闪屏；过渡只作用于颜色、背景与边框，不做位移与缩放，圆角仍为零、无阴影、无渐变。操作系统开启"减弱动效"时这套过渡整体关闭——对前庭敏感的人而言它不是装饰而是负担。

### 4.6 站点级页面与合规位

隐私与数据说明页位于 `/privacy`，内容按软件的真实行为撰写：访客无需登录即可浏览，本站不放置统计代码、埋点或第三方分析脚本；账号登录走 GitHub OAuth，本站只向 GitHub 索取公开资料（用户名、昵称、公开邮箱）用于建立或认领账号，不接触用户的 GitHub 口令，GitHub 返回的访问令牌通过 AES-256-GCM 加密后落库、仅用于拉取公开提交，不写入会话，各账号的数据与上传目录互相隔离；会话以签名 JWT 存于浏览器 Cookie，有效期 12 小时，签名密钥只在服务器环境变量中；文字内容存于自有服务器的 PostgreSQL，插图存于阿里云对象存储并使用最小权限写入密钥；已发布内容的摘要与发布时间随页公开展示，任何第三方都可独立重算核验。页内同时写明"下架"与"彻底删除"的差别，并写明已签发的会话在过期前一直有效、更换签名密钥可使全部登录态立即失效。该页进入站点地图，不需要登录即可访问。

未匹配到任何路由的地址返回统一的品牌化 404 页，给出"全部开发日志""作品档案"两个去处；渲染过程出错时由错误边界接管，页面只显示"这一页没能正常显示"与一个「重试」按钮，**有意不接收异常对象**，因此内部路径、连接信息与堆栈既不上页面也不落浏览器控制台。具体异常通过服务器日志与运维端点排查。

运维健康端点 `/api/health` 与登录无关，返回 `{"status","db"}` 两个字段：数据库可达时 200，不可达时 503。响应带 `cache-control: no-store` 与禁止索引标记，且不回显任何异常细节。

页脚常驻于前台每一页，含站点字标、隐私说明入口、开源许可入口、对外联系与侵权投诉邮箱位、两枚备案号位（ICP 与公安联网备案）以及版权行。三项合规信息全部取自环境变量，**未配置的那一项整行不渲染**——软件不用占位文案假装已合规。因此这三项在编排里必须显式传给应用容器：容器编排的环境文件只参与变量插值、不会自动注入容器，漏传会让填了的备案号依然不显示。

开源许可与致谢页位于 `/licenses`：逐项列出运行时与开发期直接依赖的名称、许可证与用途，另列三款字体及其许可，并给出第三方商标声明（说明与 GitHub, Inc. 无赞助、背书或隶属关系）。依赖许可值逐个读取各包自带的清单文件登记，不凭记忆填写；回归测试会把这份清单与项目依赖表对拍——新增依赖未登记、依赖已删除而清单未清理、或出现传染性许可（GPL / AGPL / LGPL 等）三者都会使检查失败。该页同样进入站点地图，不需要登录即可访问。

关于页位于 `/about`，静态生成，分三段：站主本人的说明（这个档案库是谁的、记什么、按什么约定维护）、技术栈、联系方式。技术栈只列名称与用途、**不写版本号**——版本的实测值唯一口径在工程约定文件里，抄进页面就多一处会漂移的地方；联系方式中的邮箱取自环境变量，**未配置时这一行显示"待补充"**，软件不写占位邮箱、也不虚构社交账号与第三方主页；同段给出本项目的公开代码仓库外链。该页进入站点地图、前台导航第三项与页脚入口，不需要登录即可访问。

## 五、管理端功能与操作说明

### 5.1 登录与登出

后台所有页面的访问前都会经过两道检查：请求进入应用前的统一守卫，以及后台布局内的会话检查。两处用的是同一个判据——会话必须带着完成 GitHub 登录后写入的账号标识，"存在会话"本身不构成放行理由。未登录访问任意后台地址会被重定向到登录页 `/login`，并携带原本要访问的地址作为回调参数。每个账号进入的是自己的控制台：概览计数、项目列表、日志编辑与全部写操作都只作用于本账号名下的数据，读取与写入在数据访问层强制附加账号条件，跨账号访问与访问不存在的记录表现一致（都按"不存在"处理），不泄露他人记录是否存在。

登录页给出一个"使用 GitHub 登录"按钮。点击后由浏览器向鉴权接口发起带防护令牌的请求，跳转到 GitHub 完成授权；首次登录时服务端按 GitHub 公开资料自动建立或认领账号（站内用户名即 GitHub 用户名），随后建立会话并跳回原地址。本站不接触用户的 GitHub 口令，GitHub 返回的访问令牌通过 AES-256-GCM 加密后落库、仅用于拉取公开提交，不写入会话。授权失败或配置缺失时回到登录页并显示通用提示，不反馈具体错在哪一步。提交期间按钮禁用并显示"登录中…"，避免连点发出多次登录请求。

会话是签名 JWT，有效期 12 小时；要立刻使全部登录态失效需更换会话密钥。登录回调端点在反向代理上限速（见第七章），超限直接返回 429。服务器会话密钥未配置或过短时，日志里会出现一条不含任何值的提示，公开页面不透露任何配置状态。后台页面右上角的"退出"一步完成：点击后直接向鉴权接口发起带防护令牌的登出请求并回到首页，不再经过框架自带的那张英文确认页，全站界面因此统一为中文；退出期间按钮同样禁用并显示"退出中…"。即使有人直接访问该登出端点，也会被指回登录页——框架那张页面在软件的任何路径上都不再出现。

### 5.2 后台概览

后台首页显示当前账号的三项计数：项目总数、已发布日志数、草稿数；其下是最近改动的五条日志，逐行标注发布状态、标题、所属项目与最后更新日期，并提供进入编辑页的链接与新建日志入口。

### 5.3 项目管理

在 `/admin/projects` 页面可以新建与编辑项目。表单字段为：标识（小写字母、数字与连字符组成，2 至 64 位）、名称（必填，不超过 80 字）、类型（产品、工具、站点三选一）、状态（进行中、已上线、已归档三选一）、简介（不超过 200 字）与仓库地址（需为 http 或 https 开头的合法地址）。

列表每行右侧提供编辑与删除操作。点击删除会先弹出浏览器原生确认框（文案为"确认要彻底删除吗？此操作不可恢复。"），点取消即阻止提交、点确认才真正提交；表单里同时置上确认位，服务端在确认位缺失时不执行删除并提示"删除没有执行：请再点一次「确认删除」。"——确认框与这一位都是防手滑而不是访问控制，脚本直接构造请求仍可带上确认位。删除时若该项目下仍挂有日志，操作会被拒绝并提示"该项目下还有日志，禁止删除。"；该项目已被其他页面删除时提示"项目不存在，可能已被删除。"（不再当作删除成功）；标识与本账号下其他项目重复时提示"slug 已被占用，换一个。"（不同账号之间标识互不冲突）；字段不合法时提示具体是哪一个字段没过关（网址里带 `&field=`，对应控件标记 `aria-invalid`）。保存与删除成功同样通过网址参数回传（`?saved=1`、`?deleted=1`）并在页面顶部以带边框的提示条显示，不依赖任何前端框架状态。

### 5.4 新建与编辑日志

新建入口为 `/admin/logs/new`。表单字段包括：标题、标识、所属项目、标签（英文逗号分隔，最多 10 个，每个不超过 24 字）、判断时间与验证时间、正文编辑器与经验总结。字段的长度与格式上限在软件里只定义一处，同时喂给服务端的校验、输入框的 `maxLength`/`pattern` 与提示文案，因此不会出现"页面允许、服务端拒绝"或反过来的漂移。

编辑器为双栏结构：左侧在判断正文与验证正文两个页签之间切换并输入 Markdown，右侧为实时预览，预览与前台使用完全相同的清洗与渲染管线，因此不会出现后台预览正常而前台异常的差异。

正文与验证正文只要偏离进入页面时的内容，就被视为"有未保存的稿子"：此时关闭标签页或刷新，浏览器会弹出自己的确认对话框拦一下——长文写到一半被误关是这个工具最贵的事故。任何一次表单提交（保存、发布、下架、彻底删除都算）会先清掉这个标记，因此不会出现"刚点了保存还被问要不要离开"。提示文案由浏览器给出，软件不代替它说话。

提交被服务端拒回时，两份正文不会丢：表单提交那一刻软件把它们暂存在这台浏览器的 sessionStorage 里，页面带着错误参数回来时一次性回填并立即清除暂存，所以不会出现"改了标题里的一个字、整篇正文一起没了"。标题、标识、标签等短字段按设计不回填（它们本身就是出错的那一项，需要重填）；暂存不落服务器、不进数据库，关闭标签页即消失。

保存后页面跳转到该条日志的编辑页并提示"已保存，当前为草稿"。草稿状态的日志在任何前台页面都不会出现，直接访问其详情地址返回 404。

编辑页会回填该条日志的全部字段，并在顶部显示当前发布状态：实心圆点加"已发布"表示前台可见，空心圆点加"草稿"表示未发布。已发布过的日志还会显示"上次发布"的摘要与时间；若当前处于草稿状态，页面会注明"这份哈希对应的是上一次发布的正文；重新发布会按当前正文重算。"

页面按需排列四个动作：保存修改、保存并发布、下架（仅已发布时出现）、彻底删除。草稿页的「保存修改」与「保存并发布」同属一张表单，后者通过按钮级的 formAction 指向发布动作，因此编辑器里当前看到的内容就是这一步要发布的内容；两者在请求在途期间一起禁用，避免同一个写动作被连点成两次执行。已发布的日志点击保存修改会立即退回草稿状态，页面提示"已发布的日志一保存就退回草稿，需要重新发布"，前台同时不再可见。

### 5.5 正文插图上传

编辑器工具条提供"插入图片"入口，点击后由系统文件选择框挑选本机图片，选择框默认只列出 png、jpeg、webp 与 gif 四类。选中文件交由服务端的上传动作处理，浏览器不持有任何对象存储凭据。

服务端按顺序完成三道判定。先校验会话，未登录返回 AUTH_001；再校验内容类型与大小——**类型判定读取文件头部的签名字节，不采信浏览器上报的 MIME 类型**：PNG 的八字节签名、JPEG 的 `FF D8 FF`、GIF 的 `GIF87a`/`GIF89a`、WEBP 的 `RIFF….WEBP` 之外一律拒绝，字节数为零或超过 5 MB 同样拒绝，均返回 IMG_001，页面提示"图片不合格：仅支持 jpg / png / webp / gif，且不超过 5MB。"因此把可执行文件改名成 .png 或伪造上报类型都无法通过；两项都通过才把文件字节写入阿里云对象存储。

写入用的对象名完全由服务端生成，形如 `logs/<账号标识>/2026-11/20261104T112157Z-72fc4931e9ca.png`，由固定前缀、当前账号标识、年月、协调世界时时间戳（大写 T 与 Z 是 ISO 格式固有的）与 12 位随机十六进制组成，扩展名取自上一步的内容签名判定结果而非上传文件名，不使用上传文件的原始名称；写入前对这个名字做逐段断言：字符集限字母（大小写）、数字、点、斜杠与连字符，且任一段不得为空、不得是 `.` 或 `..`，整体必须落在 `logs/` 前缀下——只查字符集是挡不住 `logs/../etc/passwd` 这类写法的，因为点与斜杠本身在允许集合里。账号子目录使各账号的插图在存储层分开；前缀与子账号"只允许对该前缀写入、无删除与列举权限"的最小权限策略配套（策略限定到 `logs/` 前缀，天然覆盖全部账号子目录）；地域、存储桶名与两把密钥只来自环境变量。上传经服务端动作提交，文件参数跨运行时边界到达时是二进制 Blob 而非 File 对象，服务端按 Blob 取字节并显式拒绝零字节文件。

上传成功后服务端返回公共读直链，编辑器在当前激活页签的光标位置插入 `![替代文字](直链)` 形式的 Markdown，替代文字取自文件名并剔除方括号与换行、限 60 字以内，随后焦点回到输入区并把光标移到插入内容末尾；提示条显示"已上传 · N 字节"。返回错误码时显示对应提示，请求本身异常时显示"上传失败，请查看服务端日志。"连续选择同一个文件也能再次触发，因为选择框的值在每次处理后会被清空。该分支已于 2026-11-04 端到端验通（此前因两处服务端判定写死而无法成功，见下节"上传边界"的修正记录）：以一张 70 字节的合法 PNG 提交，两次均返回"已上传 · 70 字节"，直链可被浏览器作为图片正常加载。

正文中的图片以外链形式由对象存储直接提供，服务器本地磁盘不产生任何图片文件。前台与后台预览共用同一套清洗管线，实测该管线的默认白名单包含 `img` 标签且 `src` 允许 http 与 https 协议，因此插图不会被清洗掉；图片样式限最大宽度 100% 并自动等比缩放。上传请求体的上限自下而上配成一条链：反向代理 6 MB、应用框架的动作请求体 6 MB、服务端单图判定 5 MB，三者中任一环节收紧都会让"5 MB"形同虚设，因此框架默认值（1 MB）已显式抬到 6 MB。

### 5.6 发布动作

点击「保存并发布」后，服务端先校验会话与表单，再按这张表单的内容执行一次保存，然后按**刚写入库的正文**计算摘要、记录服务器当前时间，并把摘要、发布时间与发布状态在同一次写入中完成，三者缺一不可。这一"先存再发"的顺序是为了让所见即所发：若发布只按记录标识取库中旧内容，改了正文却忘了点保存就会盖上一个与编辑器不符的摘要，而页面写的却是"按当前正文计算"。表单校验不通过时既不写入也不发布，返回 VAL_001；发布成功后页面提示"已发布，前台可见"，前台对应地址即时可访问。

摘要计算口径为：将标题、判断正文、验证正文（为空时按空字符串处理）以换行符依次拼接，取 UTF-8 编码后计算 SHA-256，输出十六进制小写字符串。该口径自第一版起固定不变，任何复核者都可以据此独立重算并与库中值比对。

已发布的日志在编辑页会多出"下架"动作：点击后服务端只把发布状态翻回未发布，前台立即不可见，而历史摘要与上一次发布时间原样保留、正文不做任何改动，页面提示"已下架，前台不再可见，历史摘要与发布时间保留"。下架与"修改正文自动退回草稿"是两条不同路径：后者由保存动作触发，前者由账号显式发起，两者的历史留痕规则一致。

### 5.7 发布前的敏感信息核对

发布动作在计算摘要之前，会先把**库中将要公开的正文**（标题、判断正文、验证正文、经验总结拼接）交给一个纯函数做形态扫描，识别九类不便公开的内容：中国大陆手机号、身份证号、云厂商 AccessKey ID、GitHub 令牌、私钥块、JSON Web Token、明文口令赋值（如 password= 后接字符串）、内网地址，以及作为提示级的邮箱地址。

两处设计细节值得写明。其一，扫描规则分两种作用域：数字形态类规则逐"词元"匹配，并整体跳过长度不小于 16 的十六进制串——否则正文里展示的 64 位内容摘要或 40 位提交号中的数字片段会被误判成手机号；而跨标点的形态（口令赋值、私钥块）必须在全文上匹配，按词元切开会永远命不中。其二，邮箱只提示不拦发布，因为联系方式常常是作者有意公开的，用它设卡只会让人关掉整个功能。

命中阻截级内容时，编辑页在动作按钮上方列出命中类别、次数与打码后的片段（片段中间以省略号截断，不重复印出完整凭据），并要求勾选"已核对上述 N 类命中，仍要发布"。未勾选时服务端返回 LOG_003 并拒绝发布，**判定发生在服务端且以库中内容为准**，因此绕过页面直接提交同样被拦；此时正文已经按这次表单存进库中，只是不对外公开——草稿本就只对自身可见，这一副作用换掉的是"发布出去的内容不是编辑器里那一份"。命中只是形态判断，允许误报（示例数据、占位串都会命中），确认后放行是有意保留的出口。

### 5.8 彻底删除

编辑页底部提供"彻底删除"表单：连正文、内容摘要与发布时间一起从数据库中移除，不可恢复，与"下架"是两条不同路径。由于不可逆，确认方式不是弹窗按钮，而是要求在原样输入框中填写该条日志的标识；服务端把输入值与库中标识比对，不一致则返回 LOG_004 并且不执行任何删除。

删除只作用于数据库中的文字内容。正文里引用过的图片对象不会被应用删除——写入对象存储使用的密钥只有上传权限，没有删除与列举权限，这是刻意的最小权限配置，为它扩权限反而降低安全性；遗留对象由存储桶的生命周期规则清理。删除成功后回后台概览并提示"该条日志已彻底删除"。

### 5.9 后台操作的结果反馈

所有写操作的成功与失败都通过页面提示条与网址参数表达，可复核、可截图留证。参数不合法、标识重复、记录不存在等情况分别对应独立错误码，详见第九章；参数类错误还在网址里带上 `&field=`，指出是哪一个字段没过关，页面把提示指向那一个控件（`aria-invalid` 与指向提示条的 `aria-describedby`），而不是一句"参数不合法"让用户逐格自查。提示条左侧的错误码标签只打系统已收录的码：网址里被手填成任意字符串时，那一格显示"未收录的错误码"，不把来路不明的串当成后台错误码展示，截图留证也不会被这类串污染。

提交进行中，同一张表单上的按钮都会立即禁用并把文案换成"保存中…/发布中…/删除中…"等，直到服务端处理结束——这是为了挡住连点：同一个"新建项目"或"发布"被点两次，就会真的写两次。禁用是整张表单范围的（框架的提交状态按表单给出），因此"保存修改"与"保存并发布"在请求在途时一起变灰，这是有意的：不允许同一条记录并发写入。按钮同时带 `aria-busy`，读屏软件能读出"忙"的状态。后台各页还提供正文地标与"跳到正文"跳转链接，键盘用户按一次即可越过整条后台导航直达正文，与前台同一套焦点样式。

## 六、数据模型与存证机制

### 6.1 数据表

系统包含三张表。用户表记录账号标识、站内用户名（唯一）、GitHub 账号标识（唯一，可空）、昵称与公开邮箱；项目表记录标识、名称、类型、状态、简介、仓库地址与所属账号；日志表记录标题、标识、所属项目、所属账号、标签数组、判断正文、验证正文、判断时间、验证时间、是否已发布、经验总结、正文摘要与发布时间，并维护创建与更新时间。项目与日志的标识在各自账号内唯一（账号与标识的复合唯一键），不同账号可用相同标识。

日志表按"是否已发布 + 判断时间"以及"所属项目"建立索引，前台列表与筛选查询直接命中索引。

### 6.2 时间处理

所有时间一律以协调世界时（UTC）存储，展示层再做转换；页面显示的发布时间明确标注 UTC 时区。表单录入使用本地时间控件，写入时转换为 UTC。

### 6.3 草稿隔离

前台读取日志的唯一入口在数据访问层强制附加"已发布"条件，页面代码无法绕过该条件查询日志表；项目页的日志条数与最近日期同样只统计已发布记录，因此草稿既不会出现在任何列表，也不会影响计数。

### 6.4 存证完整性

摘要只在发布动作时写入，与发布时间同步产生。正文任何改动都会使日志退回草稿，避免"摘要对应旧正文、页面显示新正文"的失效状态。历史摘要与历史发布时间在退回草稿时保留，供后台展示与追溯，不做清除。

## 七、安全设计

- 富文本安全：所有 Markdown 渲染统一经过清洗管线，脚本标签、事件属性与危险协议链接会被剥离；代码中不存在直接注入 HTML 的写法。
- 越权控制：后台地址在请求前置守卫与页面布局两处校验会话里的账号标识；写操作在服务端动作内部再次校验同一个标识（三处共用一个判定入口，不接受"只要有会话就放行"），不依赖前端隐藏按钮。该标识只在完成 GitHub 登录后由框架写入签名的会话令牌，浏览器无法自行伪造。数据隔离不止于准入：全部后台读取与写入在数据访问层强制附加账号条件，更新与删除按"记录标识 + 账号标识"复合执行、命中零行按资源不存在返回，因此构造他人记录标识的请求与请求不存在的记录得到同样的结果，不泄露他人数据。
- 登录限速：反向代理单独为 OAuth 登录回调端点设一条精确匹配的限速——按来源 IP 计，每分钟 5 次、允许 5 次突发且不排队；超限由反向代理直接返回 429，请求根本不进应用。其余路径不受该限制。来源地址由边缘代理以真实对端地址覆写转发头得到（不是追加），客户端自行伪造的第一跳不会被采信。
- 输入校验：所有写操作的字段长度、格式、取值范围与时间先后关系均在服务端判定，不信任浏览器提交值。这些上限在软件里只定义一处，同时供服务端校验、输入框的原生长度与格式约束、以及提示文案使用，因此不会出现某一处放宽而另一处仍拦的漂移；提交被拒时网址带上出错字段名，页面把提示指向那一个控件。记录标识先按形状校验再用于拼回跳地址与查库，外键值（所属项目）在写入前确认确实存在，避免把非法串拼进地址、也让"引用的项目不存在"变成一句可读的提示而不是数据库异常；更新与删除命中零行时按失败返回，不报告成功。
- 破坏性操作的确认层级：日志的彻底删除要求在确认框里原样输入该条标识（不匹配则不执行），点击按钮时还会先弹出原生确认框；项目的删除同样先弹原生确认框（"确认要彻底删除吗？此操作不可恢复。"），点取消即阻止提交，并置上表单确认位、服务端在确认位缺失时拒绝执行。确认框与确认位属防手滑设计，不构成访问控制：它的强度取决于登录本身，绕开页面直接构造请求仍然可以带上确认位，这一点与发布前的敏感信息勾选同口径。
- 上传边界：正文插图的内容类型（按文件头签名字节判定，不采信浏览器上报的 MIME 与文件后缀）、大小上限、对象名前缀与字符集全部在服务端裁定，对象名不使用上传文件的原始名称；写对象所使用的凭据只放在环境变量中，对应子账号仅有向固定前缀写入的权限，无删除与列举权限；服务器本地磁盘不保存任何上传图片。
- 凭据管理：数据库连接串、会话密钥、GitHub OAuth App 的 client id 与 secret、GitHub 访问令牌的加密密钥（ENCRYPTION_KEY，64 位 hex）、对象存储的两把密钥只存放在环境变量中，本地环境变量文件与生产环境变量文件均不纳入版本库；仓库内只保留不含真实值的模板文件。GitHub 访问令牌在落库前经 AES-256-GCM 加密，密文形态为 base64(iv).base64(tag).base64(ciphertext)，解密密钥即上述 ENCRYPTION_KEY。
- 传输与响应头：生产环境由反向代理终结 TLS，仅启用 TLS 1.2 与 1.3，并下发严格传输安全、内容类型嗅探禁止、来源引用策略与同源框架限制等响应头；应用容器仅绑定本机回环地址，外部流量必须经过反向代理。应用自身还随每个页面下发内容安全策略：脚本与样式只允许本站来源，页面不得内嵌任何外来对象或插件（对象标签与内嵌框架一律禁止），表单只允许提交回本站，页面也不允许被第三方站点嵌套展示——即便清洗管线之外仍有脚本被注入，它也无法把数据外送或加载外来代码；应用响应头不再携带框架版本指纹。
- 信息最小化：运维健康端点只回答"进程与数据库是否可用"两个布尔值，错误边界与 404 页不携带任何异常文本、内部路径或参数；登录相关的配置类错误在公开登录页上只说"没有配好、请查看服务端日志"，不念出任何环境变量名，具体的缺失项只出现在服务器日志里；登录后的回跳地址只接受本站相对路径，协议相对写法与用反斜杠伪装成相对路径的写法一律回到后台首页；后台与登录页在反向代理层与抓取规则层双重禁止索引。
- 凭据边界：对象存储写入使用只允许向固定前缀 PutObject 的子账号密钥，无删除与列举权限；会话密钥、GitHub OAuth 凭据、GitHub 访问令牌加密密钥与数据库口令分处环境与编排两侧，均不进入版本库。访问令牌的密文形态经 GCM 认证标签校验，篡改任何一段即解密失败。
- 凭据留痕口径：密钥与口令的轮换只在过程文档中记状态（何时轮换、旧密钥是否已删除），不记任何实际值；核实某个键是否合规时只输出派生判定（键名、值长度、是否等于模板值），不复述文件内容。成品材料交付前逐行扫描凭据形态，且先以注入的伪凭据证明扫描规则有效，再采信"未见凭据"的结论。
- 搜索引擎控制：404 响应与后台页面均带禁止索引标记。
- 数据库访问边界：数据库结构变更只能通过声明式模型文件与生成的迁移脚本完成，运行期不提供任何执行任意 SQL 的入口。

## 八、备份、升级与故障处理

- 数据备份：使用 PostgreSQL 自带的逻辑备份工具定期导出整库，备份文件存放于服务器之外的存储。
- 版本回滚：每个开发阶段形成独立提交，出现问题时按阶段回滚，不做跨阶段连环回退。
- 发版门禁：代码合并前依次跑静态检查、类型检查、生产构建与纯逻辑回归测试四条（回归测试使用运行时自带的测试跑器，不引入第三方测试框架），四条全绿才允许发版；回归用例锁定摘要口径、图片内容签名、标识与表单校验规则、错误码文案、时间展示与路由归属判定。数据库层与需登录的动作层不由其覆盖，由人工联调与运行截图留证。同一套顺序由持续集成流水线在每次提交与合并请求上代跑，门禁不依赖人记得执行。
- 材料门禁：源程序收录清单会核对源码目录，新增文件未登记即失败；生成结果要求逐字节可复现，说明正文与成品不同步同样会被拦下。收录排版按"提交窗口"设计：前后两个窗口各自必须完整容纳数据模型、核心逻辑、鉴权守卫与站点外壳，任一关键文件被窗口切口打断或整段落进省略段，生成程序即拒绝出件。
- 数据库不可用：前台页面会显示加载失败，日志与项目的详情地址返回服务端错误而非伪装成不存在，属于诚实失败，便于第一时间定位。
- 会话失效：任何后台操作遇到会话过期都会回到登录页并提示重新登录，不会静默丢失已填写内容以外的状态。
