## 二、发现的缺陷

### D1（已修复）：`/logs` 无参访问永远停在骨架

- 现象：浏览器打开 `/logs`，`main` 只有 17 个字（「开发日志 按年月归档 → 加载中…」），等待 5 秒不恢复。
- 服务端：同 URL 的 HTML 完整（含列表、`$RC("B:0","S:0")` 揭示脚本）。
- 根因：该页是 PPR 路由且读 `searchParams`，但没在等候 `searchParams` 之前声明请求期渲染，壳里只有 fallback，内容以隐藏段下发后未被揭示。
- 修复：`LogBoard` 顶部加 `await connection()`（`src/app/logs/page.tsx`）。
- 复验：`/logs` 正文长度 1897，出现「共 12 条」「排序 判断时间 / 发布时间」，列表与时间轴正常。

### D2（未解决，阻塞第 28/29 项）：带筛选/搜索参数时仍停在骨架

- 复现：`/logs?tag=WCAG`、`/logs?q=WCAG`、`/logs?q=zzzzz` 均停在骨架；`/logs`、`/logs?probe=abc`（无有效筛选）正常。
- 关键证据：同 URL 的服务端 HTML **完整**（`?tag=WCAG` 含「标签：WCAG」与 30 个 `<li>`；`?q=WCAG` 含 30 个 `<li>`；结尾都有 `$RC("B:0","S:0")`）。浏览器 DOM 里 `hidden id="S:0"` 数量为 0，`main` 仍为 fallback。
- 已排除：`searchLogsLimited` 本身没坏（`/api/search?q=WCAG` 返回 200、1 条日志 + 1 个标签）；不是缓存（清 `.next/dev` 后复现）。
- 待查方向：PPR + `searchParams` 的揭示时序、`partialPrefetching` 对带参 URL 的壳复用；下一步抓一次带参导航的 RSC 请求与 `$RV` 执行结果。
